# TrackVector: резервная одометрия трамвая по модели

[![ROS 2](https://img.shields.io/badge/ROS_2-Humble-22314E?logo=ros&logoColor=white)](https://docs.ros.org/en/humble/)
[![Ubuntu](https://img.shields.io/badge/Ubuntu-22.04-E95420?logo=ubuntu&logoColor=white)](#установка)
[![Python](https://img.shields.io/badge/Python-3.10-3776AB?logo=python&logoColor=white)](https://www.python.org/)
[![Docker Compose](https://img.shields.io/badge/Docker_Compose-v2-2496ED?logo=docker&logoColor=white)](#установка)
[![pytest](https://img.shields.io/badge/pytest-359_tests-0A9EDC?logo=pytest&logoColor=white)](#тесты)

Пакет ROS 2 Humble, который без GNSS и IMU в реальном времени считает скорость и
положение трамвая по двум скоростям тележек и позиции ручки контроллера.

**1. Модель вагона.** Таблица привода «ручка × скорость → ускорение», снятая с
реальных записей, запаздывание и инерция привода, фильтр UKF.

**2. Проверка показаний.** Каждое показание тележки сверяется с моделью и с
другой тележкой. Так нода замечает юз, буксование, отказ и залипание датчика,
шум и выбросы, а в эти моменты ведёт скорость по модели.

**3. Положение на карте путей.** Пройденный путь ложится на карту линии
(pathgraph организаторов плюс наша карта за его концами). У остановок
положение подтягивается к известной точке, у западной конечной карта знает
разворотное кольцо и боковой путь.

**4. Выход по контракту ТЗ.** 20 Гц, метки времени из bag, `/result/velocity`
в м/с и `/result/position` в системе судьи: плоские MGRS от угла квадрата
37UCB, точка `base_link`, `z` - уровень рельса. В ковариациях честная σ.

**5. Проверка на отложенных записях.** Все числа посчитаны на 15 чистых
отложенных записях против GNSS, рядом всегда наивная база «только колесо».

## Как это работает

**Шаг 1.** Нода подписана на `/vehicle/front_bogie_velocity`,
`/vehicle/rear_bogie_velocity` (км/ч) и `/vehicle/driver_position_cmd`
(−15..+15). GNSS нужен только в первые 3 с записи: для начального положения и
курса.

**Шаг 2.** Нода шагает по равномерной сетке 50 мс по меткам входов. На
каждом шаге ядро делает прогноз по ручке и принимает или отвергает показания
тележек.

**Шаг 3.** Путь вдоль колеи переводится в x, y, z по карте путей; стоянка у
остановки обнуляет накопленную ошибку пути.

**Шаг 4.** Нода публикует скорость, положение, ускорение и диагностику
(`/tram/estimator_status`: режим, срыв, сцепление, «стоим или скользим»,
достоверность).

**Шаг 5.** Если GNSS приходит и посреди маршрута (организаторы разрешили
использовать его для коррекции), нода поправляет по нему положение вдоль пути
с отбраковкой выбросов. На скорость GNSS не влияет.

## С чего начать

Поднять всё одной командой из корня репозитория: нода, проигрывание записи
(`ros2 bag play`), проба задержки, мост rosbridge и страница симулятора.

```bash
docker compose up --build
```

- **Что видно.** Страница симулятора - http://localhost:8080, мост rosbridge -
  `ws://localhost:9090`. Итог пробы (частота, задержка, CPU, память) -
  `out/probe/summary.json`.
- **Данные.** Нужна папка с записями rosbag2 из датасета кейса. По умолчанию
  это `./data` (`DATA_DIR`) и запись `30618_e9a34502` (`BAG`); другая папка или
  запись задаются в `.env` по шаблону [.env.example](.env.example), см.
  [Настройки](#настройки).
- **Версии.** Docker с Compose v2 (проверено на Docker 28.3, Compose 2.38).
- **Остальные проверки.** Без Docker, в пять шагов - [Быстрая проверка](#быстрая-проверка);
  тесты - [Тесты](#тесты).

Проверку жюри ведут на вагоне **30618**, поэтому его числа - в первых строках.

| **вагон 30618**: положение, средняя 3D-ошибка, м | 1,91 | 1,85 |
| **вагон 30618**: дрейф по концу записи, медиана, % пути | 0,032 | 0,022 |
| все 15 записей: скорость, MAE / RMSE, м/с | **0,0335 / 0,0890** | 0,0463 / 0,0948 |
| все 15: смещение скорости на торможении, м/с | **−0,0032** | +0,0482 |
| все 15: истина внутри ±2σ скорости | **96,0 %** | - |
| все 15: положение, средняя 3D-ошибка, м | 3,81 | 3,77 |
| отказ передней тележки 60 с: ошибка пути через 300 с, м (худшая из 3 записей) | **0,1** | 186,2 |
| юз −30 % обеих тележек на торможении: MAE в окне, м/с | **0,183** | 1,772 |
| реальное время: частота / задержка вход → выход p99 | 20,0 Гц / 54,2 мс | - |

Жирным выделено, где модель лучше базы. Положение у модели и у базы почти
одинаковое (у базы даже чуть лучше): его держат карта путей и привязка к
остановкам, а не модель. Модель выигрывает в скорости, особенно на торможении, и
при отказах и срывах датчиков.

## Возможности

| Возможность | Где |
|---|---|
| Скорость по модели вагона и двум тележкам, 20 Гц, с σ | `/result/velocity`, `twist.covariance[0]` в `/result/position` |
| Положение x, y, z точки `base_link` в MGRS от 37UCB, курс, σ | `/result/position` (`nav_msgs/Odometry`) |
| Ускорение по модели | `/result/acceleration` |
| Юз и буксование обеих тележек разом: флаг, знак, скорость по модели | `/tram/estimator_status`: `slip`, `slip_all` (+1 буксование, −1 юз), режим 4 |
| Отказ, залипание и обрыв датчика одной тележки: тележка исключается и возвращается сама | `wheel_healthy`, `n_accepted`, `n_rejected` |
| «Стоим или скользим»: нули обеих тележек на ходу не принимаются за остановку | `ambiguous`, `valid = false`, расширенная σ |
| Оценка сцепления и шума показаний | `mu`, `meas_noise` |
| Битые входы (NaN, метка 0, скачок времени, второй bag) не роняют ноду | [docs/ROBUST.md](docs/ROBUST.md) |
| Пауза входов: прогноз модели до 0,2 с, метки не идут назад | параметр `pulse_horizon_s` |
| Коррекция положения по GNSS посреди маршрута с отбраковкой выбросов | параметр `gnss_correction` |
| Вагон 30618 или 30639, уточнение масштаба колёс по остановкам | параметры `vehicle`, `wheel_scale_online` |
| Другая система координат выхода без правки кода | параметры `projection`, `mgrs_grid`, `output_point` |
| Замер частоты, задержки, CPU и памяти как у судьи | `tools/ros_probe.py`, `tools/measure_realtime.sh` |
| Офлайн-оценка «как судья» с базой «только колесо» и внесёнными аномалиями | `tools/eval.py` → [docs/EVAL.md](docs/EVAL.md) |
| Симулятор: песочница, реальная отложенная запись, живая нода | [simulator/](simulator/README.md) |

## Для кого и зачем

- **Пользователь.** Бортовые системы трамвая и диспетчерская, которым нужны
  скорость и положение вагона, когда GNSS нет: плотная застройка, эстакады,
  помехи, отказ приёмника.
- **Действие.**
  - Нода продолжает выдавать скорость и положение 20 раз в секунду по колёсам,
    ручке и карте путей.
  - Когда колёсам верить нельзя (юз, буксование, отказ датчика), нода ведёт
    скорость по модели, поднимает флаг и честно расширяет σ; потребитель видит
    это в `valid` и в ковариациях.
- **Срок.** Реальное время: задержка вход → выход p99 54,2 мс при допуске
  100 мс, частота 20,0 Гц при требовании ≥ 10 Гц, 10,3 % одного ядра CPU,
  70 МБ памяти.
- **Цена ошибки** (реальные отложенные записи с внесёнными аномалиями,
  [docs/EVAL.md](docs/EVAL.md) §6):
  - отказ передней тележки на 60 с: одометрия «только колесо» через 5 минут
    ошибается в пути до 186,2 м, модель - не больше 0,1 м;
  - обе тележки показывают 0 км/ч 20 с: до 206,7 м у колёс против 36,0 м у модели;
  - юз −30 % обеих тележек на торможении: скорость колёс ошибается в среднем на
    1,772 м/с, модели - на 0,183 м/с, флаг срыва стоит 99 % окна.

## Быстрая проверка

Пять шагов на чистом ROS 2 Humble (Ubuntu 22.04). Интернет и `rosdep` не нужны.
Проверено в чистом образе `ros:humble-ros-base` с `docker run --network none`:
3 пакета собираются примерно за 5 с. Ниже репозиторий лежит в
`~/vectra-tram-odometry`; если он в другом месте, поправьте путь.

1. Собрать пакеты.

```bash
source /opt/ros/humble/setup.bash
mkdir -p ~/vectra_ws/src && cp -r ~/vectra-tram-odometry/ros2_ws/src/* ~/vectra_ws/src/
cd ~/vectra_ws && colcon build && source install/setup.bash
```

2. Запустить ноду (терминал 1). При запуске она печатает блок настроек: от
строки «оценщик запущен» (версия и хэш кода) до строки «жду входы» - лист,
вагон, карта, система координат, режим GNSS.

```bash
ros2 launch tram_state_estimator tram.launch.py
```

3. Запустить пробу (терминал 2, тоже после `source ~/vectra_ws/install/setup.bash`).
Это отдельная нода с подпиской best-effort, как у судьи: она ждёт bag и после
10 с тишины печатает итог по критериям ТЗ - частота, задержка, CPU, память.

```bash
python3 ~/vectra-tram-odometry/tools/ros_probe.py --out /tmp/probe.json --idle 10
```

4. Проиграть запись (терминал 3, после `source ~/vectra_ws/install/setup.bash`).
Нода и проба должны быть запущены раньше: окно выставки по GNSS - первые 3 с записи.

```bash
ros2 bag play <путь к записи> -d 3
```

5. Посмотреть выходы (терминал 4, после `source ~/vectra_ws/install/setup.bash`).
Проверить частоту скорости (Ctrl+C - остановить).

```bash
ros2 topic hz /result/velocity
```

Показать одно сообщение положения.

```bash
ros2 topic echo /result/position --once
```

Пример вывода на короткой записи `30618_98161270` (39 с; чистый
`ros:humble-ros-base`, `--network none`):

```text
average rate: 19.998
...
header:
  frame_id: map
child_frame_id: base_link
pose:
  pose:
    position:
      x: 99052.28927254194
      y: 84985.47667747363
      z: 171.64228024920558
```

Итог пробы (терминал 2):

```text
[probe] критерий                                    | измерено                                                      | итог
[probe] --------------------------------------------+---------------------------------------------------------------+-----
[probe] частота /result/velocity ≥ 10 Гц            | 20.0 Гц по меткам, 22.0 по стенным; 852 из 852 узлов сетки    | OK
[probe] /result/position (Odometry)                 | 828 выходов, 20.0 Гц; frame_id map -> base_link               | -
[probe] задержка in2out ≤ 100 мс (p99)              | p50 48.7 / p99 53.2 мс (без первых 2 с bag)                   | OK
[probe] пик задержки ≤ 250 мс                       | max 122.5 мс; > 250 мс: 0 из 1455                             | OK
[probe] вместе со стартом bag (справочно)           | in2out(vehicle): p99 122.1, max 149.4 мс; > 250 мс: 0 из 1683 | -
[probe] CPU ≤ 2 ядра                                | ср. 9.7 % ядра, макс 23.0 %                                   | OK
[probe] ОЗУ ≤ 0,5 ГБ, без утечки                    | RSS макс 67.8 МБ, рост 0.000 МБ/мин                           | OK
[probe] NaN в выходе, плохие ковариации             | 0 / 0                                                         | OK
[probe] скорость против GNSS bag (справочно)        | MAE 0.004 м/с по 362 парам                                    | -

```

- **Задержка по пробе.** Критерий ТЗ проба считает без первых 2 с bag: там хвост
  буфера регистратора, метки на 2-6 с старше момента записи приходят пачкой.
  Строка «вместе со стартом bag» - та же задержка по всей записи, для справки.
  Подробно - [docs/JURY.md](docs/JURY.md) §6.
- **Сверка пробы с GNSS** идёт против антенны master, поэтому там около 10 м -
  это плечо от антенны до `base_link`, а не ошибка ноды.
- **Выход на ходу.** Нода раз в 10 с пишет строку состояния: частота, позиция
  ручки и режим ядра, скорость, x, y, z и их σ, сколько тележек принято.
- **Вагон 30639** - `ros2 launch tram_state_estimator tram.launch.py vehicle:=30639`.
- **Docker вместо ROS на машине.** `docker compose up --build` делает всё то же
  одной командой ([С чего начать](#с-чего-начать)); тесты -
  `docker compose run --rm test`.
- **Реальное время с лимитами ТЗ** (полная запись 20 мин, нода в контейнере
  `--cpus 2 --memory 512m`, Git Bash или Linux):
  `tools/measure_realtime.sh --bag 30618_e9a34502 --cpus 2 --memory 512m --build`,
  итог - `out/realtime/<тег>/summary.md`.
- **Windows и Git Bash.** Перед командами `docker run` с путями контейнера
  задайте `export MSYS_NO_PATHCONV=1`.

## Установка

### Docker

Скачать репозиторий и перейти в него. Все команды ниже выполняются из корня
репозитория.

```bash
git clone https://github.com/kitay-sudo/vectra-tram-odometry.git ~/vectra-tram-odometry && cd ~/vectra-tram-odometry
```

Задать папку с записями и запись для показа: в `.env` строки
`DATA_DIR=<папка с записями>` и `BAG=30618_e9a34502`. Шаг необязателен, без `.env`
действуют значения по умолчанию.

```bash
cp .env.example .env
```

`ros2_ws/src/tram_state_estimator/tools/gen_params.py`, тест `test_sheets.py`

ниже выполняются из любой папки после `source ~/vectra_ws/install/setup.bash`.


```bash

```

Запустить ноду без коррекции по GNSS посреди маршрута.

```bash
ros2 run tram_state_estimator tram_estimator --ros-args -p gnss_correction:=false
```

параметры нода берёт из него сама.

|---|---|---|

## Данные

Датасет кейса - записи rosbag2 (sqlite3) двух трамваев; описание организаторов -
[docs/DATASET_README.md](docs/DATASET_README.md), наш разбор -
[docs/DATA.md](docs/DATA.md). В репозиторий записи не входят: их папка
задаётся в `DATA_DIR` (Docker) или передаётся `ros2 bag play` напрямую.

- **Объём.** 122 записи: вагон 30618 - 103, вагон 30639 - 19; 36,75 ч.
- **Дубли.** 25 пар побайтно одинаковых записей (все - 30618 за 10.08):
  уникальных записей 97.
- **Единицы.** Скорость тележек записана в **км/ч**, а не в м/с, как сказано в
  README датасета: отношение к скорости GNSS - медиана 3,598, в отдельных
  записях от 3,54 до 3,66 (разброс - масштаб колёс вагона и даты,
  [docs/DATA.md](docs/DATA.md) §2.3). Организаторы подтвердили км/ч. Выход
  `/result/velocity` - в м/с.
- **Топики.** Тележки по 10 Гц (в среднем 9,4 Гц), ручка 20 Гц, GNSS master и
  rover по 10 Гц (`fix`, `vel`). GNSS есть в 86 записях.
- **Разбиение** ([tools/split.json](tools/split.json), строит `tools/make_split.py`):
  - `train` - 98 записей (80 уникальных): калибровка, карта оценки и выбор
    всех порогов;
  - `holdout` - 17 записей; из них `holdout_scored` - **15 чистых отложенных**
    с GNSS, без дублей и копий в обучении (12 - вагон 30618, 3 - 30639). На них
    считаются все отчётные числа.
- **Два листа и две карты.** Лист и карта ОЦЕНКИ - только по `train`
  (`config/eval/`), на них посчитаны числа отчёта. Лист и карта ЖЮРИ - по всем
  уникальным записям (`config/tram.yaml`, `config/track_map.npz`), они уходят в
  пакет.
- **Карта организаторов pathgraph** (две ломаные, по одной на направление)
  прислана 25.09 отдельно от датасета. Её исходные файлы в git не входят
  (для пересборки карт их кладут в `_incoming/pathgraph/`); точки pathgraph
  уже входят в карту пакета `config/track_map.npz`.
- **Кэш.** Офлайн-инструменты читают записи через кэш `analysis/cache/<запись>.npz`
  (в git не входит). `tools/eval.py` строит его из `data/` сам, весь кэш -
  `python3 analysis/bagio.py`.

## Воспроизведение по шагам

Все шаги - в образе пакета из корня репозитория. Собрать образ.

```bash
docker compose build
```

Открыть оболочку в образе: репозиторий на запись, записи и pathgraph - только
чтение (в Git Bash перед командой - `export MSYS_NO_PATHCONV=1`).

```bash
docker run --rm -it -v "$PWD":/repo -v <папка с записями>:/repo/data:ro \
  -v <папка pathgraph>:/repo/_incoming/pathgraph:ro -w /repo \
  -e PYTHONPATH=/repo/ros2_ws/src/tram_state_estimator:/repo/tools:/repo/analysis \
  vectra/tram:compose bash
```

Готовые результаты каждого шага лежат в репозитории, поэтому любой шаг можно
пропустить и начать со следующего.

### 1. Кэш и разбор данных

Кэш всех записей в `analysis/cache/`.

```bash
python3 analysis/bagio.py
```

Разбор датасета: частоты, единицы, метки, дубли, аномалии; итог - `out/data/`
(таблицы для [docs/DATA.md](docs/DATA.md)).

```bash
python3 tools/data_audit.py --workers 6
```

### 2. Разбиение

Разбиение по уникальным записям без утечки дублей; итог - `tools/split.json`
(лежит в репозитории).

```bash
python3 tools/make_split.py out/data/bags.csv
```

### 3. Калибровка

Листы ОЦЕНКИ (только `train`) и ЖЮРИ (все уникальные записи): таблица привода
A(u, v), запаздывание и инерция, масштаб колёс, шумы, `q_v`, выходная σ; затем
листы ноды. Около часа на 8 ядрах.

```bash
bash analysis/calib_all.sh
```

Масштаб колёс по вагонам (блок `vehicles` в калибровках).

```bash
python3 analysis/calib_vehicle.py --write
```

### 4. Карты путей

Обе карты - гибрид pathgraph и нашей карты по GNSS: остановки, конечные, ветки у
западной конечной. Собрать карту ОЦЕНКИ (только `train`).

```bash
python3 analysis/build_map.py eval
```

Собрать карту ЖЮРИ (все записи).

```bash
python3 analysis/build_map.py jury
```

### 5. Листы параметров

Листы ноды `config/tram.yaml`, `config/eval/tram.yaml`, `config/params.yaml` и
таблица «Лист параметров» в [MODEL.md](MODEL.md).

```bash
python3 ros2_ws/src/tram_state_estimator/tools/gen_params.py
```

### 6. Оценка на отложенных

15 чистых отложенных записей, лист и карта ОЦЕНКИ, GNSS только первые 3 с,
база «только колесо», 12 видов аномалий, проверка «GNSS весь прогон»; раздел
5.1 - из готовых итогов сценариев GNSS (шаг 7). Итог - `out/eval/*.json`,
[docs/EVAL.md](docs/EVAL.md) и графики `docs/img/eval_*.png`. Около 4 минут на
12 ядрах; на двух ядрах - около 8,5 минуты.

```bash
python3 tools/eval.py --variants --baseline docs/data/eval_before_r3/summary.json \
  --gnss-scenarios docs/data/eval_gnss_r3 --gnss-scenarios-before docs/data/eval_gnss_main \
  --label "итоговая (конечные и ветки у западной конечной, коррекция по GNSS, вагон)" \
  --baseline-label "прежняя версия main 56da11b: без коррекции по GNSS, параметра вагона и веток у западной конечной"
```

sha256 трёх JSON печатаются в конце раздела 1 EVAL.md. `runs.json` и
`inject.json` зависят только от данных, листа, карты и формул и совпадают с
отчётными побайтно. `summary.json` хранит ещё подпись версии (`--label`) и хэш
кода пакета, поэтому совпадает побайтно, когда оба такие же, как в шапке
EVAL.md. `--baseline-label` меняет только подпись прежней версии в разделе 0
документа. Таблицу раздела 7 `tools/eval.py` берёт из сводок замера реального
времени, которые лежат в `docs/data/realtime/` (замер - шаг 8; свои сводки -
ключ `--probe-glob`).

Второй проход и побайтное сравнение JSON.

```bash
python3 tools/eval.py --check-determinism --no-doc --out out/eval_det
```

Короткая проверка, что инструмент работает: 2 записи по 300 с, около 0,5 мин,
`docs/` не трогает.

```bash
python3 tools/eval.py --quick
```

### 7. Сценарии GNSS посреди маршрута

Семь сценариев доступности GNSS (только первые 3 с, редкие пачки, запись с
середины, весь прогон, сбои GNSS и другие) с коррекцией и без; около 20 минут
на 4 ядрах.

```bash
python3 tools/eval_gnss.py --no-naive --out out/eval_gnss
```

Пересобрать документ и графики из готовых JSON, с разделом 5.1 «Сценарии

```bash
python3 tools/eval.py --render-only --baseline docs/data/eval_before_r3/summary.json \
  --gnss-scenarios out/eval_gnss --gnss-scenarios-before docs/data/eval_gnss_main
```

### 8. ROS 2 на настоящей записи

## Границы прототипа

Полностью - [MODEL.md §0.7 и §9](MODEL.md#9-ограничения). Главное:

- **Положение держит карта.** Колёса дают только путь вдоль колеи, форму пути
  даёт карта. Вне известной линии положение ведётся по курсу, пока путь с тем
  же курсом не найдётся снова. Выбор ветки на стрелке по колёсам не виден:
  берётся преобладающая, у западной конечной - по тому, стоял ли вагон у
  платформы.
- **Без GNSS в первые секунды положения нет**, скорость есть. Окно выставки -
  3 с от первой точки GNSS master; ноду нужно запустить до bag.
- **Масштаб колёс меняется по датам** (до 1,2 % у одного вагона) сильнее, чем
  между вагонами (0,38 %). Нода уточняет его по остановкам; у одной отложенной
  записи 30618 это уточнение ошиблось на 0,7 %, поэтому MAE вагона 30618 -
  0,0266 м/с, а без уточнения было 0,0261 ([docs/EVAL.md](docs/EVAL.md) §0,
  [docs/VEHICLES.md](docs/VEHICLES.md)).
- **Плавный срыв обеих тележек** (нарастает за 0,5 с и дольше, или меньше 20 %
  скорости) не отличить от разгона: распознаётся только резкий.
- **Отказ обеих тележек сразу после трогания** (ниже 2 м/с) выглядит как
  остановка: в песочнице модель 20 с считает, что вагон стоит, ошибка скорости
  до 10,8 м/с ([docs/SANDBOX.md](docs/SANDBOX.md) §6).
- **Длительный юз с блокировкой колёс двусмыслен**: «стоим или скользим» по
  этим входам не различить. Модель помечает оценку недостоверной и расширяет σ.
- **Коррекция по GNSS посреди маршрута** доверяет RTK; долгий сбой RTK
  (десятки секунд) она примет. Без RTK делаются только малые поправки.
- **Пауза записи входов около секунды**: прогноз идёт только 0,2 с, дальше
  выход молчит до возвращения входов (на `30618_af7496f0` разрыв выхода 0,85 с);
  задержка после паузы - до 181,5 мс. Точки GNSS, пришедшие во время такой
  паузы, ждут возвращения входов тележек и ручки
  ([Результаты](#результаты), реальное время).

## Развитие

План по порядку пользы, у каждого пункта - какое ограничение он снимает и какой
критерий затрагивает, - [MODEL.md §10](MODEL.md#10-план-развития). Ближайшие шаги:

1. Признавать стоянку по длительности нулей при тормозной команде; не принимать
   «стоим», если ручка долго держит тягу.
2. Плавный возврат пути после снятия неоднозначности вместо скачка.
3. Детектор плавного юза и буксования по расхождению колёс с моделью на
   длинном окне, с уклоном из карты.
4. Граф путей со стрелками вместо «преобладающей ветки».
5. Уклон из профиля высот карты - прямо в уравнение движения.
6. Дополнительные входы, если они есть в вагоне: двери, стояночный тормоз, ток
   тяговых двигателей. Они снимают двусмысленность «стоим или скользим».

## Топики и сообщения

Входы (подписка best-effort, глубина 50):

| Топик | Тип | Как используется |
|---|---|---|
| `/vehicle/front_bogie_velocity` | `tram_vehicle_msgs/msg/VelocitySensor` | скорость передней тележки, км/ч |
| `/vehicle/rear_bogie_velocity` | `tram_vehicle_msgs/msg/VelocitySensor` | скорость задней тележки, км/ч |
| `/vehicle/driver_position_cmd` | `tram_vehicle_msgs/msg/DriverControllerCommand` | позиция ручки −15..+15 |
| `/sensing/gnss/master/fix`, `/sensing/gnss/rover/fix` | `sensor_msgs/msg/NavSatFix` | первые 3 с - начальное положение и курс по двум антеннам; дальше, если есть, - поправка положения вдоль пути. На скорость не влияет |

Выходы (издатель reliable, глубина 10; подписчик best-effort с ним совместим),
метки `header.stamp` - время из bag, узлы сетки кратны 0,05 с:

| Топик | Тип | Частота | Что внутри |
|---|---|---|---|
| `/result/velocity` | `tram_vehicle_msgs/msg/VelocitySensor` | 20 Гц | `velocity` - продольная скорость, м/с; `frame_id` `base_link` |
| `/result/position` | `nav_msgs/msg/Odometry` | 20 Гц | `pose.pose.position` - x, y, z точки `base_link` в MGRS от угла 37UCB; `orientation` - курс; `pose.covariance[0]`, `[7]` - σ² положения; `twist.twist.linear.x` - скорость, `twist.covariance[0]` - её σ²; `frame_id` `map`, `child_frame_id` `base_link` |
| `/result/acceleration` | `geometry_msgs/msg/AccelStamped` | 20 Гц | продольное ускорение по модели, м/с² |
| `/tram/estimator_status` | `tram_msgs/msg/EstimatorStatus` | 20 Гц | диагностика, поля ниже |

`/result/position` публикуется с первой годной точки GNSS master; до неё идёт
только скорость. Система координат и как её поменять -
[docs/JURY.md §4](docs/JURY.md#4-система-координат-положения).

Поля `EstimatorStatus` ([EstimatorStatus.msg](ros2_ws/src/tram_msgs/msg/EstimatorStatus.msg)):

| Поле | Смысл |
|---|---|
| `mode` | 0 выбег, 1 тяга, 2 торможение, 3 переход, 4 срыв, 5 стоянка, 6 деградация |
| `v`, `s`, `sigma_v`, `sigma_s` | скорость и путь по модели, их σ |
| `d`, `k_traction`, `k_brake`, `mu` | возмущение (уклон, масса), масштабы тяги и торможения, оценка сцепления |
| `slip`, `slip_all` | признак срыва; срыв обеих тележек разом: +1 буксование, −1 юз |
| `ambiguous` | «стоим или скользим»: колёса не различают, скорость ведёт модель |
| `meas_noise` | оценка шума показаний тележек, м/с |
| `wheel_healthy`, `n_accepted`, `n_rejected`, `odometry_used` | какие датчики исправны, сколько показаний принято и отвергнуто на шаге |
| `axle_scale` | калибровочные масштабы тележек (в порядке `wheel_healthy`) |
| `valid` | оценка достоверна |
| `frame_count`, `sensor_stamp`, `step_time_us` | счётчик шагов, метка исходных данных, время шага ядра |

Посмотреть поля на ходу.

```bash
ros2 topic echo /tram/estimator_status --field mode
```
