## 1. Система координат

Ответ организаторов 25.09: «плоские координаты именно в MGRS», оси по REP-103.

| | Что |
|---|---|
| Внутренняя система ноды | UTM зоны точки выставки (здесь 37) со сдвигом в точку выставки: x = E − E0, y = N − N0, z — абсолютная высота. Непрерывная: карта, счисление, привязки к остановкам идут в ней |
| Выход `/result/position` | перевод только при публикации (`geodesy.Frame.out`), по параметру `projection` |
| `projection: mgrs` (по умолчанию) | x — восток, y — север в 100-км квадрате MGRS, z — абсолютная высота (как `NavSatFix.altitude`) |
| `mgrs_grid: ""` (по умолчанию) | каждая точка в своём квадрате (соглашение Autoware `gnss_poser` / lanelet2 `MGRSProjector`): на границе x прыгает на 100 км |
| `mgrs_grid: "37UDB"` | непрерывно от угла этого квадрата: западнее E = 400 км x < 0 |
| `projection: utm` | абсолютные E, N зоны; z — высота |
| `projection: enu` | строгий ENU WGS84 от точки выставки (первая точка master) |
| `projection: equirect` | прежняя формула напарника (x = Δλ·a·cos φ0, y = Δφ·a, z = Δh) |
| `utm_zone` | 0 — зона по точке выставки; для `mgrs_grid` зона берётся из кода |
| Курс (`orientation`) | курс сетки UTM для mgrs/utm; для enu/equirect повёрнут на сближение меридианов |

Геодезия своя, без pyproj: UTM рядами Крюгера до n⁶ (Karney 2011), MGRS
(пояс, буквы столбца и строки схемы AA). Сверено с PROJ 9.5.1 (14 точек в
разных зонах и полушариях: E, N расходятся меньше чем на 2e-9 м, обратное —
на 5e-9 м; сближение меридианов и масштаб — до 1e-6) и с NGA GeoTrans (пакет
`mgrs`: 14 строк MGRS совпали, в том числе 37UCB и 37UDB на нашей линии).
Ревьюер повторил на 400 случайных точках: 6,5e-9 м, 400 из 400 строк MGRS.

## 2. GNSS только для выставки (C2, WP1)

| Правило | Как сделано |
|---|---|
| Окно | ±`init_window_s` (3 с) от первой годной точки (раньше неё — хвост буфера записи в начале bag) |
| Точка вне окна | отбрасывается сразу, без шага сетки |
| Точка в окне | ставится в очередь и применяется, когда сетку (её двигают только тележки и ручка) доведут до её метки. **GNSS сетку не двигает никогда** — сильнее, чем П3 из CONTRACT |
| Якорь и путь выставки | пересчитываются только при точке, вошедшей в выставку |
| Проверка точки | конечные lat/lon, не (0, 0), `status ≥ 0`; `altitude = NaN` → высота карты, иначе последняя годная |
| Сбой метки | точка с меткой дальше 30 с от сетки ядра отбрасывается; если такая точка пришла до тележек и открыла окно, окно открывается заново от первой разумной точки (`Position.resync`) |
| До первой годной точки | `pos_valid = False`, нода `/result/position` не публикует (в MGRS «(s, 0, 0)» — это 6000 км) |

Почему у критика на `30639_92226df0` и `30639_d3c43d69` скорость расходилась до
0,65 / 0,61 м/с (воспроизведено: `diff before,a1`). В стартовом всплеске bag
точки GNSS с метками на 3–6 с вперёд приходят в первые 0,3 с записи (74 из 134
точек окна по времени записи имеют метку > t0 + 3 с). Старый `on_fix` вызывал
`_advance` и доводил сетку до этих меток раньше, чем приходили показания
тележек с более ранними метками: показания попадали не в свои шаги. На 30639
решение гейта стоит на грани, и это дало всплеск на t0 + 3…4 с длиной ~1 с;
средняя 3D не менялась. Теперь GNSS сетку не двигает вовсе.

Побочный эффект, который пришлось закрыть: фаза сетки зависела от первого
сообщения. На 4 прогонах, начинавшихся с точки GNSS, узлы совпадали с метками
GNSS (кратны 0,1 с), без GNSS — нет, и MAE скорости росла 0,032–0,036 →
0,043–0,047. Поэтому первый узел теперь `floor(stamp/dt)·dt` (WP23): узлы
кратны 0,05 с на всех прогонах.

## 3. Выставка и запасные режимы (WP14)

| Ситуация | Якорь | Курс |
|---|---|---|
| Стоим в окне (путь колёс за окно < 0,3 м) | среднее точек master окна без выбросов (> 20 м от медианы); если выбросами оказались все (две точки или два облака дальше 40 м) — ближайшие к медиане, якорь никогда не NaN | по парам master→rover одной эпохи (±0,06 с, база 5–25 м) |
| Едем в окне (старт на ходу) | последняя точка master окна, путь колёс — на её метку | то же |
| Нет rover, едем | как выше | по смещению master за окно (> 5 м) |
| Нет rover, стоим, есть карта | как выше | по карте: ближайшая точка < 3 м, иначе самая «езженая» в пределах 30 м |
| Нет rover, стоим, нет карты | как выше | нет курса: выход стоит в якоре |
| **Нет master** (rover ≥ 1 с без master) | точка rover (как выше), сдвинутая назад по курсу на базу 12,42 м (rover впереди); пришёл master — выставка заново по master | по смещению rover, иначе по карте; без курса — точка rover |
| Сдвиг «GNSS окна − карта» | **по умолчанию не переносится** (`keep_offset_max_status: -1`, раздел 7.4); 1 — только без RTK, 2 — всегда | — |

## 5. Онлайн-масштаб пути (WP13)

По привязкам к остановкам: множитель = (s0·3000 + Σ(L_i·s0·m + δ_i)) / (3000 + ΣL_i),
δ_i — сдвиг вдоль пути при привязке, L_i — путь колёс с прошлой привязки (≥ 100 м).
Ограничения: ±1 %; отрезок со сдвигом > 1 %·L + 2 м не учитывается; если
множители принятых отрезков расходятся > 1,2 %, подстройка выключается и
множитель возвращается к 1. Вклад на holdout (умолчания `H`): 4,11 → 3,97 м;
`30639_92226df0` 6,13 → 4,33 м; худший прогон 30618 — `a53d5f6f` 1,04 → 1,17 м
(+0,13). На train без подстройки 4,41 м против 3,81 м (при ×1,000, раздел 7.4).

## 8. Ограничения

* Соглашение судьи на границе 37UCB/37UDB неизвестно (раздел 1); защита 20 м
  стоит ~5 с без положения на пересечение и не спасает при ошибке вдоль пути
  больше 20 м (старт на ходу).
* Эталон судьи — master (по ответу организаторов антенны равноправны; tf между
  ними обещан). Если эталон — rover или середина базы, +5…11 м (аудит POSITION §2).
  База 12,42 м в запасном режиме «нет master» — по данным, до tf.
* Западная конечная: рейсы в тупиковый путь дают ~55 м в конце (раздел 4).
* 30639 без RTK (`3b3d9eb8`, `d3c43d69`): эталон сам смещён на метры (высота
  до 8 м), ошибка 8–23 м.
* Без карты положение — километры (стоянка или прямая), это физика задачи без
  гироскопа.

## 9. Как повторить

```bash
# образ vectra/tram:dev, из корня репозитория, данные и кэш смонтированы
python3 analysis/build_map.py eval          # EVAL-карта (train)
python3 analysis/build_map.py jury          # карта в пакет (все прогоны)
C=--calib ros2_ws/src/tram_state_estimator/config/tram_calibration.json
python3 tools/position_eval.py run --tag H $C                      # полный прогон ядра (~5 мин, 3 процесса)
python3 tools/position_eval.py run --tag H_guard0 --replay $C --opt mgrs_guard_m=0.0   # только положение
python3 tools/position_eval.py run --tag H_nomap --replay $C --map none
python3 tools/position_eval.py run --tag H_full --gnss full $C
python3 tools/position_eval.py run --tag H_cut --scenario cut $C   # norover | nomaster | cut | cut_norover
python3 tools/position_eval.py run --tag trG --ids train --replay $C   # обучающие (выбор умолчаний)
python3 tools/position_eval.py score --tag H
python3 tools/position_eval.py report --tags before,H,... --runs   # --detail H
python3 tools/position_eval.py diff --tags H,H_full                # C2: max |dv|, |dp|
python3 tools/position_eval.py boundary                            # кто пересекает E = 400 км
cd ros2_ws/src/tram_state_estimator && python3 -m pytest test/test_position.py -q
```

Скрипты, которыми посчитаны таблицы 1, 4, 7.4 (в `out/fix/`, вне
репозитория): `guard_sweep.py <тег с g = 0> 0,5,10,20` — полоса защиты по
одному прогону; `gap.py` — разрыв карты; `groups.py` — средние по группам RTK;
`edge_new.py` — сбои выставки на реальных прогонах. Сценарии запускались
скриптами `run_train*.sh`, `run_hold2.sh` там же.

`before` — код `main` (56933cc) с картой напарника из обучающих прогонов
(`analysis/cache/track_map_train.npz`, те же 98 прогонов train), его
выход в своей формуле (equirect от первой точки master) и эталон в той же
формуле: это лучший для старого кода вариант. Против MGRS старый выход
(относительный) ошибается на десятки километров.
