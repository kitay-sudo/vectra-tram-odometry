## 1. Что делает нода с плохими входами

| Что пришло | Что происходит | Где |
|---|---|---|
| метка ≤ 0, NaN, inf, не число | сообщение отбрасывается целиком, сетка не двигается | `Runner._advance` |
| одиночный скачок метки > 10 с (вперёд или назад) | сообщение отбрасывается, в `t_wheel` / `t_notch` не пишется | `Runner._advance` |
| скачок > 10 с, подтверждённый вторым сообщением (новый bag, `--loop`) | полный сброс: ядро, выставка (`Position`), `s0`, стоянка, сетка, отметки входов; WARN в лог; выставка по GNSS нового прогона | `Runner.reset` |
| стартовый «хвост буфера» bag (метки назад на 1,1–2,7 с) | не трогается: порог 10 с | — |
| скорость тележки NaN, ±inf, не число, \|v\| > 1,5·`v_max_line` (108 км/ч по листу) | значение отбрасывается, метка двигает сетку | `Runner.on_wheel` |
| ручка NaN / inf | отбрасывается; вне ±15 — ограничивается до ±15 | `Runner.on_handle` |
| состояние ядра стало неконечным (последний рубеж) | ядро пересоздаётся, путь сохраняется, шаг повторяется | `Runner._step_safe` |
| разрыв больше, чем `MAX_STEPS` = 200 шагов за вызов | лишние узлы пропускаются (при dt = 50 мс и пороге 10 с не бывает) | `Runner._run_to` |
| исключение в колбэке | лог ERROR раз в 5 с, нода живёт; 20 ошибок подряд — сброс связки | `tram_node._input` |
| процесс всё же упал | launch перезапускает (`respawn=True`, `respawn_delay=1.0`) | `tram.launch.py` |
| Ctrl+C | выход без трассировки: `ExternalShutdownException`, второй SIGINT игнорируется, `rclpy.try_shutdown()` | `tram_node.main` |
| неконечный x/y/z на выходе | заменяется последним конечным, WARN | `tram_node._publish` |

GNSS (`on_fix`, `Position`) — зона потока position; `Runner.on_fix` вызывает `_advance`, и отброшенная метка там видна как `self.stamp_ok == False`.

## 2. Время и сетка

- **WP23.** Узлы сетки кратны `dt`: `t = (k0 + n)·dt`, `k0 = floor(первая метка / dt)`, `n` — целый счётчик. Узлы совпадают с метками GNSS (кратны 0,1 с), дрейфа накопления `t += dt` нет. Прежняя фаза: `Runner.grid_align = False`.
- **WP6.** Свежее показание тележки приводится к моменту шага: `z + a·(t − метка)`, `a` — ускорение модели на прошлом шаге, возраст ограничен 0,3 с. Не трогаются нулевые показания и показание, равное прошлому (залипший датчик должен остаться видимым для диагностики ядра). Выключается `Runner.age_comp = False`.
- **WP24.** Первые `start_sort_s` = 0,1 с по монотонным часам нода копит входы и отдаёт их по порядку меток: стартовый всплеск bag (≈200 сообщений за 0,1 с, метки на 3–4 с назад) исполнитель rclpy разбирает по топикам, а не по меткам, и сетка начиналась позже самой ранней метки.
- **WP16, пульс.** Таймер по монотонным часам (10 мс; работает и с `use_sim_time` без `/clock`). Если узел сетки просрочен на `pulse_margin_s` = 0,1 с (без ручки — `pulse_margin_nohandle_s` = 0,03 с) относительно «метка последнего входа + прошедшее время», нода публикует прогноз на копии связки (`Runner.fork()`: ядро, выставка, курсор копируются, карта и лист общие). Горизонт `pulse_horizon_s` = 2 с от последней метки. Когда входы возвращаются, связка продолжает со своего состояния; её узлы, уже выданные прогнозом, второй раз не публикуются, метки выхода не идут назад.

## 3. Лист без `--params-file` (WP22)

Если ни одного параметра ядра не передано (`ros2 run tram_state_estimator tram_estimator`), нода берёт значения по умолчанию из `share/tram_state_estimator/config/tram.yaml`; явно переданные `-p` остаются. Параметр `sheet`: `auto` (так), путь к листу, `none` (заглушки `Params`, для имитатора). В лог INFO пишется, какой лист и какая карта загружены:

```
оценщик запущен: шаг 50 мс, карта есть; лист: .../config/tram.yaml (без --params-file: лист пакета); карта: .../config/track_map.npz; единицы km_h; пульс 2.0 с
```

`tram.launch.py` принимает `params_file:=...` (по умолчанию лист пакета).

## 4. Ковариации Odometry (WP12a)

Нулевых диагоналей нет. Нуль в ROS значит «известно точно», это неправда.

| Элемент | Значение | Обоснование |
|---|---|---|
| pose x, y | σ_s² ядра; до выставки 1e6 | путь вдоль колеи, изотропно; до выставки абсолютное положение неизвестно |
| pose z | 1 м²; до выставки 1e6 | высота из карты (усреднённый GNSS) |
| крен | (0,05 рад)² | возвышение наружного рельса в кривой до ~3° |
| тангаж | `theta_max`² = (0,06 рад)² | уклон линии по листу |
| курс | (0,05 рад)²; до выставки 1e6 | ось пути карты, ~3° |
| twist vx | σ_v² ядра | |
| twist vy | (0,05 м/с)² | вагон на рельсах, боковой скорости нет |
| twist vz | (v·theta_max)² + 0,05² | скорость по уклону |
| угловые x, y | (0,02 рад/с)² | крен и тангаж почти постоянны |
| угловая z | (v / 20 м)² + 0,02² | рыскание не оцениваем (0), наименьший радиус кривой трамвая ~20 м |

## 8. Ограничения и компромиссы

- **Подтверждённый скачок > 10 с внутри одного прогона** считается новым прогоном: выставка теряется, без GNSS положение идёт от нуля (фаззинг `clock_back_100s`: 1155 м). В данных таких скачков нет (максимум 1,05 с).
- **Первое сообщение нового прогона** — кандидат разрыва и теряется (одно сообщение).
- **Пауза плеера** (метки стоят, стенные часы идут): прогноз заполняет первые `pulse_horizon_s`, а после возобновления столько же времени узлы не публикуются, иначе метки пошли бы назад. Общая длина тишины не меняется. При настоящем пропуске данных (метки идут дальше) прогноз закрывает до 2 с без провала после.
- **Провал записи bag** (метки непрерывны, запись с опозданием ~1 с): то же — прогноз, затем пауза той же длины. В `af7496f0` максимум разрыва 0,95 → 0,78 с.
- **Сортировка старта** задерживает первые 0,1 с входов на ≤ 0,1 с (in2out этих ~200 сообщений растёт).
- **Старт bag при нагрузке.** В 4 прогонах с инъектором (`rb_nan`, `rb_inf`, `rb_stamp0`, `rb_handle127`) нода получила первое сообщение на 2–2,5 с позже пробы: DDS-обнаружение плеера под нагрузкой (так было и в аудите: эксп. 8d–8f 1032–1140 выходов). Код ноды здесь ни при чём.
- **GNSS alt = NaN** (фаззинг `gnss_nan_alt`): `z` связки NaN до конца — это `Position.on_fix` (поток position). В ROS нода подменяет неконечные x/y/z последними конечными.
