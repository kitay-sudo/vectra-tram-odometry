# Датасет: разбор записей

Разбор 122 записей датасета: топики, единицы, метки времени, дубли, аномалии и что из них следует
для пакета. Все числа - выход [`tools/data_audit.py`](../tools/data_audit.py) (rosbags 0.10.9,
раздел 7); по каждой записи - [`docs/data/bags.csv`](data/bags.csv), дубли -
[`docs/data/pairs.csv`](data/pairs.csv). Модель и калибровка - [MODEL.md](../MODEL.md), защита от
плохих входов - [ROBUST.md](ROBUST.md), масштаб колёс по вагонам и датам - [VEHICLES.md](VEHICLES.md).

**Обозначения.** «уник.» - 97 уникальных записей (дубли выброшены); F/R - передняя/задняя

Координаты - плоские ENU (м) от 55.80484N 37.42050E, как в `analysis/build_map.py`.

## 1. Сводка фактов и следствия для решения

В каждом пункте сначала факт, затем следствие для пакета.

1. **122 bag = 97 уникальных записей.** 25 пар побайтно одинаковы (sha1 всех сообщений с метками
   записи), все - вагон 30618 за 2026‑08‑10. Частичных перекрытий нет. Уникальных часов 28,66
   из 36,75.
   *Следствие:* перед калибровкой и оценкой дубли убираются (колонка `dup_of` в `bags.csv`), иначе
   25 записей получают двойной вес.

2. **Разбиение по именам даёт утечку.** Исходное разбиение `sorted(ids)[2::5]`
   (`analysis/calib_drive.py`) даёт 24 отложенных, у 6 из них точная копия в обучении; пара
   `21dd3af3 = f3b8c99b` целиком в отложенных (раздел 4).
   *Следствие:* разбиение для отчёта собрано по уникальным записям (`tools/split.json`). Листы и
   карты ОЦЕНКИ - только по `train`, ЖЮРИ - по всем. Отчётные числа - на 15 чистых отложенных
   ([MODEL.md](../MODEL.md) §0.2).

3. **Ровно 7 топиков во всех 122 прогонах**, типы как в README датасета. Pathgraph, tf и IMU нет.
   `metadata.yaml` совпадает с содержимым: число сообщений, начало, длительность.
   *Следствие:* карты путей в датасете нет. Pathgraph организаторы прислали отдельно; карта пакета -
   pathgraph плюс наша карта из GNSS за его концами ([POSITION_FRAME.md](POSITION_FRAME.md) §3).

4. **Скорость тележек в км/ч, а не в м/с, как пишет README.** Отношение тележки/скорость GNSS:
   медиана 3,598 (70 уник. с GNSS); по хордам между точками fix - 3,605 (п. 5).
   *Следствие:* показания делятся на 3,6. Выход `/result/velocity` - в м/с.

5. **Масштаб колёс зависит от вагона и даты.** 30618: 3,594-3,603 (07‑27…08‑26), но 3,543-3,578
   на 09‑03. 30639: 3,618-3,658 на 05‑05 и 3,587-3,591 на 08‑26. Разброс ±1-1,9 %. Доплеровская
   скорость и хорды fix дают одно и то же: меняется масштаб колёс, а не скорость GNSS
   (раздел 2.3).
   *Следствие:* один `meas_scale` на всё даёт 50-100 м ошибки пути на 5,4 км без привязки к
   остановкам. Окна старта (3 с стоянки) для оценки масштаба мало, а проверочная дата неизвестна.
   Поэтому вагон задаётся параметром `vehicle`, а масштаб даты оценивается онлайн по остановкам:
   `wheel_scale_online` для скорости, медленнее `scale_adapt` для положения
   ([VEHICLES.md](VEHICLES.md)).

6. **Метки тележек и GNSS в одной шкале.** Лаг тележки↔GNSS по меткам 0,00 с (−0,05..0,00,
   70 уник.), остаток 0,030 м/с. По времени записи лучший лаг −0,05 с (30618), остаток 0,034, при
   нулевом лаге 0,039. Лаг F↔R 0,00 с в обеих шкалах.
   *Следствие:* шаг идёт по `header.stamp`, выходы штампуются метками входа.

7. **Хвост буфера на старте каждого bag.** За первые 0,1-0,3 с записи приходит 2,1-6,2 с (медиана
   3,5 с) истории всех 7 топиков вперемешку, 97-296 сообщений. В порядке записи метки разных
   топиков идут назад до 1,1-2,7 с.
   *Следствие:* нода не «прыгает» по первой метке: стартовый всплеск сортируется, порог скачка
   назад 10 с ([ROBUST.md](ROBUST.md) §1, §2).

8. **Сбои меток ±1 с.** На входах - 3 уник. прогона (`2255aade`, `40ffd323`, `9c362687`): десятки
   сообщений с меткой на ±1,0 с от соседей вперемешку с нормальными. На GNSS - 15 уник. прогонов,
   худшие: `30639_3b3d9eb8` (метки всех 4 GNSS-топиков на 1 с впереди подряд 579-822 с, около
   2 420 сообщений на топик) и `30618_40ffd323` (по ~600 сообщений на топик на −1 и +1 с на
   отрезке 85-506 с).
   *Следствие:* без защиты метка +1 с дала бы 20 шагов сразу и ~1 с тишины: провал частоты и
   пропуск пар у судьи. Связка проверяет метки против базы времени
   ([ROBUST.md](ROBUST.md) §1, §2а).

9. **Тележки записаны с задержкой 22-69 мс** (медиана 46 мс; прогоны > 2 мин), ручка - ~1 мс. В
   порядке прихода 5,7 % входных сообщений (медиана по прогонам) опаздывают > 50 мс относительно
   уже достигнутой метки, максимум 0,08-0,10 с.
   *Следствие:* без поправки показание попадало бы в шаг на шаг-два позже своей метки: на разгоне
   1 м/с² это до ~0,08 м/с систематики (оценка по задержке, не замер). Показание приводится к
   моменту шага ([ROBUST.md](ROBUST.md) §2).

10. **На старте вагон стоит во всех 97 уник.** Максимальная скорость за первые 3 с - 0,12 м/с. За
    10 с трогаются 51 из 97 (30639 - 16 из 19).
    *Следствие:* статическая выставка по GNSS за 3 с корректна для этих данных; окно не должно
    захватывать трогание.

11. **GNSS есть не во всех записях.** Master fix+vel в 86 bag (77 уник.). Только rover (4 Гц,
    плохой) - `30639_e4379d7f`. Без GNSS 35 bag (19 уник.), все - 30618 за 08‑10.
    `30618_1551d0a9` длится 1,3 с. Где GNSS есть, он начинается ≤ 0,024 с от начала bag и идёт
    до конца.
    *Следствие:* положение можно оценить на 77 уник. записях, скорость - на 76 (у `1551d0a9` меньше
    50 сообщений vel). Остальные записи - только для привода и ручки.

12. **Точности GNSS в данных нет.** NavSatFix: `status` master 2 (GBAS) 81,1 %, 0 (FIX) 18,8 %,
    1 (SBAS) 0,07 %, −1 нет; `service` = 1. `position_covariance_type` = 0 и все ковариации = 0
    в 100 % сообщений.
    *Следствие:* качество эталона оценивается по `status`: в прогонах со `status` 0 эталон хуже
    (п. 13).

13. **Эталон GNSS сам с дефектами.** Скачки fix (медиана 4 на прогон, до 552), нулевая скорость
    GNSS на ходу (228 отсчётов, 182 в `4d487b0d`), выброс `vel.z` до 40,8 м/с, разрывы vel до
    33 с. Трек `30639_9c362687` смещён на 16 м от треков 30618 (у 30639 ещё `44226bde` - 3,0 м,
    `253671cc` - 1,8 м), у самих 30618 медиана смещения 0,015 м. Во всех трёх записях 30639
    преобладает `status` 0: доля `status` 2 - 0,06 / 0,00 / 0,29.
    *Следствие:* метрики читаются с поправкой на эталон: карта «абсолютная», а эталон в прогоне
    без RTK сдвинут. Сдвиг «карта − GNSS» из окна выставки можно сохранить в выходе
    (`keep_offset_max_status`), по умолчанию выключено: на обучающих записях выигрыша нет.

14. **Один маршрут.** Трамвайная линия ~5,4 км между двумя конечными с разворотными петлями
    (раздел 2.5). Оба вагона, оба направления: В→З 34, З→В 34 уник. записи, остальные
    короткие или стоянка. 447 клеток 25 м на всё; 30618 и 30639 делят 322.
    *Следствие:* карта из данных покрывает только эту линию, pathgraph организаторов - её же. Вне
    карты положение ведётся по курсу ([MODEL.md](../MODEL.md) §0.7).

15. **База и оси GNSS.** База master-rover 12,40-12,44 м (медиана 12,418), rover впереди. `vel` в
    ENU (x = восток, y = север, z = вверх; корреляция с производной позиции 0,98-1,00).
    `twist.angular` всегда 0.
    *Следствие:* курс на старте - по вектору master→rover, скорость эталона - `hypot(x, y)`.

16. **Высота GNSS гуляет.** Высота master 108,8-227,5 м. Размах за прогон: медиана 28,9 м, до 82 м
    (с выбросами GNSS).
    *Следствие:* `z` берётся из карты, а не из GNSS в ходе прогона.

17. **Ручка.** Используются все позиции −15..+15: нейтраль 34,5 % сообщений, тяга 35,0 %, тормоз
    30,5 %. 20 Гц; в метаданных 2 издателя (2 QoS‑профиля) во всех bag, но дублей меток нет.
    Трогание при тормозной ручке: 32 из 814 троганий с места (3,9 %); 63 эпизода ≥ 2 с (279 с)
    «ручка ≤ −8, а ускорение > 0,3 м/с²». Типично: ручка проходит 0→−15 за 3 с, вагон
    разгоняется до 8-11 м/с с 1,0-1,4 м/с².
    *Следствие:* знак ручки местами инвертирован, причина неизвестна. Ручке нельзя верить больше,
    чем колёсам: согласие тележек сильнее модели ([MODEL.md](../MODEL.md) §0.3).

18. **Аномалий входов мало.** NaN/Inf нет. Застывших ненулевых показаний ≥ 2 с нет. Ноль одной
    тележки при езде другой - ≤ 0,8 с. Отрицательные скорости только в 2 уник. (до −0,39 км/ч,
    обе тележки сразу: откат). Расхождение F/R: медиана 0,032 км/ч, p99 0,25. Эпизодов с
    расхождением |F−R| > 3 км/ч всего 11 (13,6 с, до 15,4 км/ч) в 6 уник. Провалы одной
    тележки на 30639: задняя до 73,5 с (8 из 19 прогонов, до 104 с суммарно), передняя до 19,8 с.
    *Следствие:* юз и буксование в данных редки, поэтому устойчивость проверяется инъекцией
    аномалий ([EVAL.md](EVAL.md) §6). Провал одной тележки - реальный сценарий на 30639.

19. **«Застывший датчик» на деле провал.** То, что похоже на застывшее показание 1,28 м/с, - это
    провал задней тележки на 47,1 с в `30639_4285f2bc`: сообщений нет, до провала 0, после
    4,62 км/ч = 1,28 м/с. Одинаковых повторов нет.
    *Следствие:* диагностика «застывания» по повтору значения здесь не сработает. Нужен тайм-аут
    свежести по меткам - `wheel_timeout_s`.

20. **Частоты.** Тележки номинально 10 Гц (медианный интервал записи 0,100 с), средняя 9,38 Гц,
    p99 интервала 0,2 с. Ручка 20 Гц. GNSS fix/vel 10 Гц, метки GNSS строго кратны 0,1 с.
    Разрывы > 0,5 с на входах у 30618 только одновременные у обеих тележек, до 1,25 с (в части
    случаев и у ручки): остановка записи.
    *Следствие:* шаг ядра 50 мс по меткам корректен. Одновременный провал обеих тележек на ~1 с
    должен переживаться без сброса.

- **Типы.** Тележки - `tram_vehicle_msgs/VelocitySensor`, ручка -

- **frame_id.** Тележки - `base_link`, ручка - пусто, GNSS - `gps`.

- **Объём.** Всего 8 788 325 сообщений: F 1 239 220, R 1 237 408, ручка 2 652 391, master fix/vel
  927 147 / 895 750, rover 921 272 / 915 137.
- **Длительность.** 1,3 с…31,6 мин, медиана 19,8 мин. Короче 2 мин 11 уник. записей: стоянки или
  отладочные куски, ручка 0.

### 2.2. Метки времени

- **Заполнены везде.** `header.stamp`: 0 нулевых, 0 повторов подряд. Внутри топика метки
  монотонны, кроме сбоев ±1 с (п. 8).
- **Порядок строк.** В sqlite строки лежат по возрастанию времени записи. Исключение - одна строка
  в 7 bag (5 уник.) на участках сбоев.
- **Хвост буфера (п. 7).** Пример `30618_0e41eac3`: первое сообщение (rear) имеет смещение 3,53 с,
  ручка 3,44, fix 2,22, rover vel 0,63. Нормальный режим (смещение < 0,1 с) наступает через
  ~0,13 с записи.
- **Природа сбоев ±1 с.** Это не гонка sec/nanosec: сдвинутые метки идут по всей секунде
  (мс 31-935). Похоже на ступеньку часов источника, которая держится от 1 до сотен секунд.
- **Что увидит нода.** `ros2 bag play` публикует в порядке записи, поэтому нода увидит и хвост
  буфера, и сбои (п. 7-9).

## 4. Дубликаты и утечка в обучение

**Метод.** Для каждого bag считается sha1 по всем сообщениям 7 топиков (топик + время записи +
сырые байты CDR) и отдельно по потокам трёх входов. Частичные копии ищутся по 64-битным хэшам
каждого сообщения передней тележки (пересечение множеств у всех пар одного вагона) и по
пересечению интервалов записи.

**Результат.** 25 групп по 2 bag, в каждой паре совпадает всё, включая метки записи. Частичных
копий и перекрытий по времени между разными записями нет. Все 25 пар - 30618 за 2026‑08‑10:
57 bag за эту дату = 32 уникальные записи. В 16 парах нет GNSS, в 9 есть. Список пар -
[`docs/data/pairs.csv`](data/pairs.csv).

**Утечка исходного разбиения.** Разбиение - `calib_drive.split`: `ids[2::5]` по отсортированным
именам.

| Что | Число |
|:---|---|
| Отложенных bag / уникальных записей среди них | 24 / 23 |
| Отложенные с точной копией в обучении | **6**: `0a83c933`, `2f2f1175`, `6cb3280a`, `79b204dc`, `8eb8615c`, `b1098bdb` |
| Из них с GNSS (попадают в `analysis/evaluate.py`) | 1: `6cb3280a` (копия `f3a0694d` в обучении) |
| Оцениваемых `evaluate.py` (есть ≥ 50 сообщений master vel) | 17 bag = 16 уник.; одна запись (`21dd3af3`) считается дважды |
| Чистых уникальных отложенных с GNSS | **15** |
| Пар «обе копии в обучении» | 18: двойной вес 18 записей в калибровке |

**Утечка помимо дублей.** Лист ЖЮРИ (с таблицей привода) и карта ЖЮРИ собраны по всем уникальным
записям, включая отложенные. Поэтому отчётные числа считаются на листе и карте ОЦЕНКИ, собранных
только по `train` ([MODEL.md](../MODEL.md) §0.2): `tools/eval.py`, 15 чистых отложенных записей
([EVAL.md](EVAL.md)). Все 6 дат есть и в обучении, и в отложенных, поэтому сдвиг масштаба колёс по
датам (п. 5) отложенная выборка не проверяет; его разбор по обучающим записям -
[VEHICLES.md](VEHICLES.md) §6.

## 7. Как пересчитать

Команда выполняется из любой папки: репозиторий и папка с записями подключаются томами.

Пересчитать разбор всех записей.

```bash
docker run --rm -v <репозиторий>:/repo -v <папка с записями>:/repo/data:ro -w /repo \
  vectra/tram:compose python3 tools/data_audit.py --workers 6
```

То же в PowerShell.

```powershell
docker run --rm -v <репозиторий>:/repo -v <папка с записями>:/repo/data:ro -w /repo `
  vectra/tram:compose python3 tools/data_audit.py --workers 6
```

| Опция | Что делает |
|:---|---|
| `--workers 6` | число процессов, по умолчанию не больше 6 и не больше числа ядер |
| `--bags ID ...` | разобрать только указанные записи |
| `--out <папка>` | папка выхода, по умолчанию `out/data` |

Выход лежит в `out/data/`, каталог `out/` в git не входит.

| Файл | Что внутри |
|:---|---|
| `bags.csv` | строка на прогон, около 190 колонок; копия - [`docs/data/bags.csv`](data/bags.csv) |
| `topics.csv` | строка на пару «прогон × топик» |
| `pairs.csv` | дубликаты; копия - [`docs/data/pairs.csv`](data/pairs.csv) |
| `summary.json` | агрегаты по всем и по уникальным записям |
| `bags_table.md` | компактная таблица по прогонам (раздел 3) |
| `routes.png`, `handle_hist.png` | картинка маршрутов и гистограмма ручки |

- **Время.** Около 4,5 мин на 6 процессах.
- **Повторяемость.** Скрипт детерминирован: два прогона (6 и 4 процесса) дали побайтно одинаковые
  `bags.csv`, `topics.csv`, `pairs.csv`, `summary.json`, `bags_table.md`.
