# Инструкция для жюри

> Версия от 27.09.2026. Числа точности взяты из [EVAL.md](EVAL.md): 15 чистых
> отложенных записей, лист параметров и карта путей только по обучающим
> записям. Проверки сборки, ROS 2 и реального времени этой версии - раздел 9.

Пакет решает кейс «Резервная одометрия по модели». Нода получает скорости двух
тележек и позицию ручки контроллера. По ним она в реальном времени публикует
скорость и положение трамвая. GNSS нужен только в первые 3 с bag, для начальной
выставки положения. Если GNSS есть и дальше, нода поправляет по нему положение
вдоль пути (`gnss_correction`, по умолчанию включено; выбросы отбрасываются,
[POSITION_FRAME.md](POSITION_FRAME.md) §12). На скорость GNSS не влияет.

## 1. Коротко

Собрать пакеты в чистом ROS 2 Humble, интернет не нужен (`<репозиторий>` - папка
клона, команды выполняются из любой папки).

```bash
source /opt/ros/humble/setup.bash
mkdir -p ~/vectra_ws/src && cp -r <репозиторий>/ros2_ws/src/* ~/vectra_ws/src/
cd ~/vectra_ws && colcon build && source install/setup.bash
```

Запустить ноду в терминале 1: сначала нода, потом bag.

```bash
ros2 launch tram_state_estimator tram.launch.py
```

Проиграть bag в терминале 2 (здесь тоже после `source ~/vectra_ws/install/setup.bash`).

```bash
ros2 bag play <путь к прогону> -d 3
```

Выход: `/result/velocity` и `/result/position`, 20 Гц, метки времени из bag.
Положение - точка `base_link` в плоских MGRS от угла квадрата 37UCB (непрерывно),
`z` - высота уровня рельса (раздел 4).

## 1а. Проверка скриптом организаторов (check-code)

Организаторы выдали образец проверки: нода `hackathon_solution_checker` сравнивает
`/result/velocity` и `/result/position` с эталоном `/localization/kinematic_state` из
записи (пары по меткам времени, допуск 0,05 с; RMSE и максимум ошибки).

- **Пакет сообщений.** В архиве проверки свой `tram_vehicle_msgs` только с
  `VelocitySensor`. Наш содержит тот же `VelocitySensor` (файл совпадает байт в байт) и
  `DriverControllerCommand` (ручка). Скопируйте наши пакеты в их `src/`: папка
  `tram_vehicle_msgs` совпадёт по имени, и останется один пакет, наш. Если наш
  репозиторий лежит отдельной папкой, colcon сообщит «Duplicate package names»; тогда
  отключите их копию: `touch src/tram_vehicle_msgs/COLCON_IGNORE`.
- **Без типа ручки нода не падает.** Если собран только их пакет сообщений, нода пишет
  «Внимание: в tram_vehicle_msgs нет DriverControllerCommand, ручка не используется» и
  работает по тележкам.

Повторить проверку организаторов одной командой (из корня репозитория, нужен Docker;
сборка в чистом `ros:humble-ros-base`, 2 ядра, 512 МБ, запись в реальном времени, около
23 мин).

```bash
tools/judge_check.sh --check <папка check-code>
```

Результат на их записи `30618_88aea4d9` (22 мин, итоговая версия пакета до правки
горизонта пульса; числа из вывода их ноды):

| Метрика | Значение |
|---|---|
| скорость, RMSE / максимум | 0,059 / 0,320 м/с |
| положение 3D, RMSE / максимум | 1,43 / 11,26 м |
| x, y, z, RMSE | 1,28 / 0,64 / 0,10 м |
| пар скорости и положения | 26 233 |

## 2. Сборка без Docker

В `ros2_ws/src/` три пакета:

| Пакет | Что это |
|---|---|
| `tram_vehicle_msgs` | сообщения кейса (`VelocitySensor`, `DriverControllerCommand`), те же `.msg`, что в датасете. В манифест добавлен `<maintainer>`: без него `colcon build` в Humble падает |
| `tram_msgs` | наше сообщение диагностики `EstimatorStatus` |
| `tram_state_estimator` | нода `tram_estimator` (Python), лист параметров `config/tram.yaml`, карта путей `config/track_map.npz`, launch |

Что нужно:

- ROS 2 Humble (`ros-humble-ros-base`). Используются только пакеты базового образа:
  `rclpy`, стандартные сообщения, `launch`, `launch_ros`, `python3-numpy`,
  `python3-yaml`.
- `rosdep` не нужен, интернет не нужен. Проверено в чистом `ros:humble-ros-base`
  с `docker run --network none`: 3 пакета собираются за 5-12 с, нода стартует.
- Если в вашем workspace уже есть `tram_vehicle_msgs` из датасета, оставьте
  **один** (colcon не соберёт два пакета с одним именем). Поля сообщений у них
  одинаковые. Наш отличается только строкой `<maintainer>`, берите наш.

## 3. Запуск

1. **Сначала нода, потом bag.** Нода подписывается на входы при старте. Сообщения,
   которые bag опубликует до подписки, до неё не дойдут. Окно выставки по GNSS -
   первые 3 с bag. Если нода их пропустит, положения в этом прогоне не будет.

   ```bash
   source ~/vectra_ws/install/setup.bash
   ros2 launch tram_state_estimator tram.launch.py
   ```

   При запуске нода печатает блок настроек. Нода готова, когда в логе есть
   строка «жду входы» (пример из нашего прогона, префиксы логгера убраны):

   ```text
   оценщик запущен: tram_state_estimator 0.1.0, код sha <16 знаков>
     лист: .../share/tram_state_estimator/config/tram.yaml [/tram_state_estimator] (...)
     вагон 30618: meas_scale 1.001362 (общий лист 1.001093), онлайн-масштаб колёс вкл.
     карта есть: .../share/tram_state_estimator/config/track_map.npz (точек осей 17554, остановок 51, конечных 4, веток у конечных 3)
     выход mgrs от квадрата 37UCB непрерывно; точка base_link (карта по base_link); frame_id map, child_frame_id base_link
     GNSS: выставка по первым 3.0 с; коррекция по GNSS после окна вкл (только положение вдоль пути, скорость от GNSS не зависит)
     шаг 50 мс (20 Гц) по header.stamp входов; единицы km_h; пульс 0.2 с; QoS входов best-effort
     жду входы: /vehicle/front_bogie_velocity, /vehicle/rear_bogie_velocity, /vehicle/driver_position_cmd, /sensing/gnss/master/fix, /sensing/gnss/rover/fix
   ```

   `код sha` - отпечаток кода пакета. Тем же способом посчитан «Код пакета: sha»
   в шапке [EVAL.md](EVAL.md): совпадают - числа отчёта посчитаны на этом коде;
   не совпадают - код менялся после расчёта (пересчёт - раздел 7).
   Когда пойдёт bag, нода напишет «входы пошли», затем «положение есть с метки …»
   (выставка по GNSS прошла) и дальше раз в 10 с - строку состояния: частота,
   позиция ручки и режим ядра, скорость, x, y, z и их σ, сколько тележек принято.

   **Вагон.** По умолчанию нода настроена на вагон 30618 (проверка идёт на нём).
   Для записи вагона 30639 - `ros2 launch tram_state_estimator tram.launch.py
   vehicle:=30639`, для неизвестного вагона - `vehicle:=auto` (общий лист по обоим).
   Масштаб колёс, если он у записи другой (другая дата), нода уточняет сама по
   остановкам (`wheel_scale_online`, включён в листе).
   Разница вагонов и что она даёт - [VEHICLES.md](VEHICLES.md).

   **Рекомендуем `ros2 launch`**: он подставляет лист `config/tram.yaml` и
   перезапускает ноду при падении (`respawn`). `ros2 run tram_state_estimator
   tram_estimator` без `--params-file` тоже работает правильно: нода сама берёт лист
   пакета. В логе тогда будет «без --params-file: лист пакета». Проверено: выход
   такой же, как у launch.

2. **Bag - в любом режиме.** Организаторы подтвердили, что режим проигрывания не
   важен. Нода работает по `header.stamp` входов. Поэтому `--clock` и `use_sim_time`
   не нужны, но и не мешают.

   ```bash
   source ~/vectra_ws/install/setup.bash
   ros2 bag play <путь к прогону> -d 3
   ```

   `-d 3` даёт DDS 3 с, чтобы плеер нашёл подписчиков до первого сообщения. Под
   нагрузкой обнаружение занимало до 3,7-5,8 с после старта плеера. Поэтому ноду
   запускайте заранее, а bag - с задержкой не меньше 3 с. Скорость `-r` может быть
   любой: нода сама оценивает темп проигрывания.

3. **Несколько bag подряд.** Лучше перезапускать ноду между прогонами: Ctrl+C и
   снова `ros2 launch`. Тогда каждый прогон получает свою выставку по GNSS. Без
   перезапуска тоже работает. Разрыв меток (назад больше 10 с или вперёд больше
   60 с: второй bag, `--loop`) нода распознаёт как новый прогон и выставляется заново по его GNSS. Проверено: второй
   bag раньше первого на 142 с - 1 сброс, новая выставка, ошибка в конце 0,24 м.

4. **Останов** - Ctrl+C в терминале ноды. Выход без трассировки.

## 3а. Если в ваших bag GNSS есть и посреди маршрута

Организаторы 26.09: GNSS гарантирован в первые секунды записи; посреди маршрута
сообщения «могут быть» и их можно использовать для коррекции, но топик будет
пуст или почти пуст. Нода к этому готова, настраивать ничего не нужно:

- **Первые 3 с** - выставка, как всегда.
- **Дальше** каждая точка GNSS - кандидат поправки положения **вдоль пути**
  (поперёк держит карта). Вес точки - по `NavSatFix.status`: RTK (2) - σ 0,5 м,
  без поправок (0) - σ 5 м. Выбросы отбрасываются: скачки, метки не по часам
  тележек (дальше 0,3 с от последнего входа), пары антенн со сбитой базой.
  Большая поправка (больше 3 м) - только по RTK и только после 3 согласных
  эпох подряд; без RTK - только малые поправки, не чаще раза в 20 с.
- **Скорость GNSS не трогает никогда**: сетка, скорость, σ скорости и
  диагностика те же, что при GNSS только в первые 3 с (проверено на каждом
  шаге, [EVAL.md](EVAL.md) раздел 5).
- Если GNSS в начале записи не было (запись с середины), первая годная точка
  открывает выставку заново.
- Выключить коррекцию: `-p gnss_correction:=false` - тогда GNSS только для
  выставки.

Что это даёт на наших отложенных записях вагона 30618 - [EVAL.md](EVAL.md)
раздел 5.1; как устроено - [POSITION_FRAME.md](POSITION_FRAME.md) §12.

## 4. Система координат положения

По ответам организаторов: плоские координаты **MGRS**, оси по REP-103 (x - восток,
y - север, z - вверх). Их карта pathgraph записана от угла квадрата **37U CB
непрерывно**: x = UTM E − 300 000, y = UTM N − 6 100 000. На границе квадратов
E = 400 км x переходит через 100 000 плавно, без скачка. Точка вагона -
**`base_link`**: ось поворота передней тележки на уровне касания колеса и рельса.

| Ось | Значение на выходе |
|---|---|
| `x` | MGRS easting от угла 37U CB, м (на линии около 98 800…103 700) |
| `y` | MGRS northing от угла 37U CB, м |
| `z` | высота уровня рельса, м, в той же системе, что `z` pathgraph (судья считает ошибку по x, y и z - ответ 26.09 22:38). На карте `z` берётся из карты: в части pathgraph - его `z`, за его концами - высота антенн по GNSS записей датасета минус 3,0 м. Без карты - `altitude` из `NavSatFix` минус 3,0 м (высота антенн над `base_link`) |

`frame_id` = `map` (эта система), `child_frame_id` = `base_link`. Положение
публикуется на каждом шаге после первой годной точки GNSS master. До неё
`/result/position` не публикуется, а `/result/velocity` идёт с первого шага.

Антенны в `base_link` по tf организаторов: master (−9,873; 0; 3,0), rover
(2,563; 0; 3,0). При выставке нода считает `base_link = master + 9,873/12,436 ·
(rover − master)`, `z` минус 3,0 м. Дальше точка ведётся по карте путей. Карта
построена по траектории `base_link`: pathgraph организаторов плюс наша карта из
GNSS записей датасета за его концами. Подробно - [POSITION_FRAME.md](POSITION_FRAME.md).

Всё это задаётся параметрами в `config/tram.yaml`:

| Параметр | Значения | По умолчанию |
|---|---|---|
| `projection` | `mgrs` - плоские MGRS; `utm` - UTM E/N зоны 37; `enu` - касательная плоскость в первой точке master; `equirect` - прежняя формула | `mgrs` |
| `mgrs_grid` | код квадрата - непрерывно от его угла; `""` - у каждой точки свой квадрат (как Autoware, на границе скачок на 100 км) | `"37UCB"` |
| `mgrs_guard_m` | только при `mgrs_grid: ""`: ближе этого к краю квадрата положение не публикуется; `0` - выключено | `0.0` |
| `output_point` | `base_link` - ось передней тележки, уровень рельса; `master` - антенна master (на 9,87 м позади и на 3 м выше) | `base_link` |
| `antenna_master_x`, `antenna_rover_x`, `antenna_z` | положение антенн в `base_link`, м | `-9.873`, `2.563`, `3.0` |
| `origin_lat`, `origin_lon`, `origin_alt` | начало для `projection: enu`; NaN - первая точка master | NaN |
| `init_window_s` | окно выставки по GNSS от первой точки, с | `3.0` |
| `gnss_correction` | GNSS после окна выставки поправляет положение вдоль пути (с отбраковкой выбросов); `false` - GNSS только для выставки | `true` |
| `vehicle` | вагон: `30618` (проверка организаторов идёт на нём), `30639` или `auto` - общий лист по обоим вагонам; неизвестное значение - как `auto` с предупреждением в логе | `30618` |
| `wheel_scale_online` | онлайн-масштаб колёс по остановкам: если путь по карте и путь колёс между остановками (от двух отрезков по 300 м) расходятся больше чем на 0,5 %, скорость поправляется (не больше ±2 %). Учится только по положению без поправок GNSS | `true` |
| `map_file` | карта путей; `""` - без карты | `config/track_map.npz` |
| `nomap_mode` | без карты: `hold` - стоять в точке выставки, `line` - по прямой вдоль начального курса | `hold` |
| `pulse_horizon_s` | прогноз при паузе входов, с от последней метки; `0` - выключен | `0.2` |

**Как поменять.** Без правки файлов - параметром запуска. Остальные параметры нода
возьмёт из листа пакета.

Запустить ноду с другим квадратом отсчёта.

```bash
ros2 run tram_state_estimator tram_estimator --ros-args -p mgrs_grid:=37UDB
```

Запустить ноду с выходом в точке антенны master.

```bash
ros2 run tram_state_estimator tram_estimator --ros-args -p output_point:=master
```

Или в файле: `~/vectra_ws/install/tram_state_estimator/share/tram_state_estimator/config/tram.yaml`
(либо `src/.../config/tram.yaml` с пересборкой). Исправьте строку под
`ros__parameters` и перезапустите launch. Свой лист целиком:
`ros2 launch tram_state_estimator tram.launch.py params_file:=<путь к листу.yaml>`.
Все параметры есть в листе с комментариями. Лист генерирует
`ros2_ws/src/tram_state_estimator/tools/gen_params.py`, а тест `test_sheets.py` сверяет его с объявлениями ноды.

## 5. Топики

Входы (подписка best-effort, глубина 50):

| Топик | Тип | Как используется |
|---|---|---|
| `/vehicle/front_bogie_velocity` | `tram_vehicle_msgs/msg/VelocitySensor` | скорость передней тележки, км/ч (подтвердили организаторы; в README датасета - м/с) |
| `/vehicle/rear_bogie_velocity` | `tram_vehicle_msgs/msg/VelocitySensor` | скорость задней тележки, км/ч |
| `/vehicle/driver_position_cmd` | `tram_vehicle_msgs/msg/DriverControllerCommand` | позиция ручки −15..+15 |
| `/sensing/gnss/master/fix`, `/sensing/gnss/rover/fix` | `sensor_msgs/msg/NavSatFix` | окно выставки (`init_window_s` = 3 с от первой точки): начальное положение и курс по двум антеннам. Если GNSS есть и дальше - поправка положения вдоль пути (`gnss_correction`, раздел 3а). На скорость не влияет |

Выходы (издатель reliable, глубина 10; подписчик best-effort с ним совместим):

| Топик | Тип | Частота | `frame_id` | Что внутри |
|---|---|---|---|---|
| `/result/velocity` | `tram_vehicle_msgs/msg/VelocitySensor` | 20 Гц | `base_link` | `velocity` - продольная скорость, м/с |
| `/result/position` | `nav_msgs/msg/Odometry` | 20 Гц | `map`, `child_frame_id` = `base_link` | `pose.pose.position` - x, y, z (раздел 4); `orientation` - курс; `pose.covariance[0]`, `[7]` - σ² положения, м²; `twist.twist.linear.x` - скорость; `twist.covariance[0]` - σ² скорости. Нулевых диагоналей нет ([ROBUST.md §4](ROBUST.md#4-ковариации-odometry)) |
| `/result/acceleration` | `geometry_msgs/msg/AccelStamped` | 20 Гц | `base_link` | продольное ускорение модели, м/с² |
| `/tram/estimator_status` | `tram_msgs/msg/EstimatorStatus` | 20 Гц | `base_link` | режим (тяга, выбег, торможение, срыв, стоянка), σ скорости и пути, μ, `slip`, `slip_all` (+1 буксование, −1 юз), `ambiguous` («стоим или скользим»), `meas_noise`, принято и отвергнуто тележек, `valid` |

**Метки времени.** `header.stamp` всех выходов - время из bag, а не часы ноды.
Нода шагает по равномерной сетке 50 мс по меткам входов. Каждый шаг публикуется с
меткой своего узла. Узлы кратны 0,05 с, метки монотонны.

**Глубина очереди подписчика - не меньше 50.** В начале bag записан хвост буфера:
несколько секунд меток приходят за доли секунды. Нода обрабатывает его пачкой, до
49 выходов за один вызов. Подписчик best-effort с глубиной 10 и медленным колбэком
может потерять часть этих выходов.

**Паузы входов и конец bag.** Если входы молчат дольше 0,1 с (пауза в записи или
пауза плеера), нода публикует прогноз модели. Прогноз идёт не дальше 0,2 с от
последней метки входа. Метки выхода при этом не идут назад. Горизонт короткий
намеренно: узлы, выданные прогнозом, вернувшиеся после паузы входы повторно не
публикуют, и их выход ждёт до горизонта (раздел 6, запись с паузой входов). После
конца bag выходит ещё до 0,2 с прогноза (до 4 выходов). Отключить:
`-p pulse_horizon_s:=0.0`.

**Наше определение задержки (in2out).** Время по стенным часам пробы от приёма
входа `/vehicle/*` до приёма первого выхода со `stamp ≥ stamp` этого входа. В этом
выходе показание уже учтено. Около 50 мс заложено схемой: показание попадает в
следующий узел сетки 50 мс.

**Оговорка про старт bag.** Первые 2-3 с каждой записи - хвост буфера регистратора.
Метки сообщений там на 2-6 с старше момента записи, и они приходят пачкой. Поэтому
критерии задержки проба проверяет без первых 2 с bag (в JSON - поле
`latency.in2out_vehicle_steady_ms`). Та же задержка по всей записи, вместе с
пачкой, - строка «вместе со стартом bag (справочно)», в JSON -
`latency.in2out_vehicle_ms`: на коротком bag её p99 бывает больше 100 мс. Если
считать задержку как `now() − header.stamp` по `/clock`, первые секунды bag дадут
до 2,5 с «задержки». Это свойство записи, а не ноды.

## 8. Docker

Всё то же в контейнере одной командой. Нужен Docker с Compose v2, команды выполняются
из корня репозитория.

Задать папку с прогонами (`DATA_DIR`) и прогон для показа (`BAG`); без `.env`
действуют значения по умолчанию.

```bash
cp .env.example .env
```

Поднять ноду, проигрывание bag, пробу, мост и страницу.

```bash
docker compose up --build
```

Собрать пакеты (`colcon build`) и прогнать тесты без сети.

```bash
docker compose run --rm test
```

Прогнать отдельно тест времени шага.

```bash
docker compose run --rm test -m timing
```

Запустить офлайн-оценку `tools/eval.py` (раздел 7).

```bash
docker compose run --rm eval
```

`--build` нужен после каждого обновления исходников: нода запускается из образа.
Интернет нужен только при сборке образа (apt, pip `rosbags`). Сборка пакетов внутри
образа сеть не использует. Базовый образ закреплён по digest.

| Сервис `docker compose up` | Что делает |
|---|---|
| `estimator` | `ros2 launch tram_state_estimator tram.launch.py` |
| `player` | ждёт подписчиков (ноду и пробу) и выполняет `ros2 bag play /data/$BAG -d 5` (`PLAY_DELAY`); `PLAY_LOOP=1` - по кругу |
| `probe` | `tools/ros_probe.py`; итог - `out/probe/summary.json` |
| `bridge` | rosbridge `ws://localhost:9090`, только для чтения |
| `web` | страница симулятора `http://localhost:8080` |

Скрипты проверки (Git Bash или Linux, из корня репозитория; образ по умолчанию у
всех трёх - `vectra/tram:compose`, если его нет, скрипт соберёт его сам; `--build`
у `ros_smoke.sh` и `ros_e2e.sh` пересобирает пакеты из рабочего дерева внутри
контейнера, у `measure_realtime.sh` - образ).

Прогнать ROS-смоук на фикстуре из git, данные не нужны.

```bash
tools/ros_smoke.sh
```

Прогнать ROS-смоук на 30 с настоящего прогона из `DATA_DIR`.

```bash
tools/ros_smoke.sh --bag 30618_98161270
```

Проиграть bag целиком через ноду.

```bash
IMAGE=vectra/tram:compose tools/ros_e2e.sh --bag 30618_af7496f0 --build
```

Проверить ноду на NaN во входе.

```bash
IMAGE=vectra/tram:compose tools/ros_e2e.sh --bag 30618_bab2fe58 --inject "nan --at 15 --dur 3" --build
```

Замерить реальное время с лимитами ТЗ.

```bash
tools/measure_realtime.sh --bag 30618_e9a34502 --cpus 2 --memory 512m --build
```

`ros_smoke.sh` проверяет: не меньше 19 Гц; in2out p99 меньше 100 мс; не меньше 95 %
узлов сетки; 0 NaN; `frame_id`; нода жива до конца; останов по SIGINT.

## 10. Если что-то не так

| Симптом | Причина и что делать |
|---|---|
| `colcon build`: `Duplicate package names` | два `tram_vehicle_msgs` в workspace - оставить один, наш (раздел 2) |
| `colcon build`: ошибка catkin_pkg про maintainer | собирается оригинальный `tram_vehicle_msgs` без `<maintainer>` - взять наш |
| `ros2 bag play`: не найден тип `tram_vehicle_msgs/...` | в терминале плеера не выполнен `source install/setup.bash` |
| выходов нет | нода запущена после bag или в другом `ROS_DOMAIN_ID` / `ROS_LOCALHOST_ONLY`. Проверить `ros2 node list`, запустить ноду раньше bag |
| `/result/position` не публикуется, скорость есть | нода не получила GNSS master в начале bag (запущена поздно или в bag нет GNSS). Перезапустить ноду, bag с `-d 3` |
| x около 3 400 вместо около 103 400 | нода запущена с `mgrs_grid: ""` (у каждой точки свой квадрат). Вернуть `"37UCB"` |
| положение на ~10 м позади и на 3 м выше эталона | `output_point: master`. Вернуть `base_link` |
| в итоге пробы «положение против антенны master» (у `ros_smoke.sh` - «точность по GNSS из bag») около 10 м | сверка пробы идёт против антенны master, а выход - `base_link` (раздел 6) |
| выход 100 Гц, скорость неверная | нода запущена с `sheet: none` (заглушки имитатора) - убрать этот параметр |
| в логе нет «карта есть» | не найден `config/track_map.npz` в `share/tram_state_estimator` - пересобрать пакет. Без карты положение стоит в точке выставки (`nomap_mode: hold`) |
| первые секунды частота больше 20 Гц, задержка по `/clock` до 2,5 с | хвост буфера записи в начале bag (раздел 6) |
| подписчик теряет выходы на старте | глубина очереди меньше 50 (раздел 5) |
| Docker: порт 9090 или 8080 занят | `BRIDGE_PORT` / `WEB_PORT` в `.env` |
| Docker: сборка остановилась с `image … already exists` | Compose собирал один тег параллельно. Повторить команду или `COMPOSE_BAKE=false docker compose up --build` |
| Docker: `player` пишет «bag не найден» | `DATA_DIR` в `.env` - папка с каталогами прогонов; `BAG` - имя каталога |
