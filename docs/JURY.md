# Инструкция для жюри

> **Версия после слияния всех потоков (26.09.2026, ветка `integration`).**
> Команды и интерфейс ноды — окончательные. Числа точности — `docs/EVAL.md`
> (15 отложенных прогонов, оценочные лист и карта); проверки сборки, ROS и
> реального времени этой версии — раздел 8 и `docs/audit/INTEGRATION.md`.

Пакет решает кейс «Резервная одометрия по модели»: по скоростям двух тележек и
положению ручки контроллера нода в реальном времени публикует скорость и
положение трамвая. GNSS используется только в первые секунды bag для начальной
выставки.

## 1. Кратко

```bash
# сборка (чистый ROS 2 Humble, интернет не нужен)
source /opt/ros/humble/setup.bash
mkdir -p ~/vectra_ws/src && cp -r <репозиторий>/ros2_ws/src/* ~/vectra_ws/src/
cd ~/vectra_ws && colcon build && source install/setup.bash

# терминал 1 — нода (рекомендуем launch: перезапуск при падении)
ros2 launch tram_state_estimator tram.launch.py
# терминал 2 — bag (в терминале тоже выполнить source install/setup.bash)
ros2 bag play <путь к прогону> -d 3
```

Выход: `/result/velocity` и `/result/position`, 20 Гц, метки времени из bag.

## 2. Состав и сборка без Docker

В `ros2_ws/src/` три пакета:

| Пакет | Что это |
|---|---|
| `tram_vehicle_msgs` | сообщения кейса (`VelocitySensor`, `DriverControllerCommand`) — те же `.msg`, что в датасете. В манифест добавлен `<maintainer>`: без него `colcon build` в Humble падает (catkin_pkg) |
| `tram_msgs` | наше сообщение состояния `EstimatorStatus` |
| `tram_state_estimator` | нода `tram_estimator` (Python), лист параметров `config/tram.yaml`, карта путей `config/track_map.npz`, launch |

Сборка — команды из раздела 1. Требования:

- ROS 2 Humble (`ros-humble-ros-base`). Используются только пакеты базового
  образа: `rclpy`, стандартные сообщения, `launch`, `launch_ros`, `python3-numpy`,
  `python3-yaml`.
- **`rosdep` не нужен.** `rosdep check --from-paths src --ignore-src` в чистом
  `ros:humble-ros-base` без сети: «All system dependencies have been satisfied».
- **Интернет не нужен.** Проверено в `ros:humble-ros-base` с `docker run --network none`:
  3 пакета собираются за 27 с (2 CPU), нода стартует (раздел 8).
- Если в вашем workspace уже есть свой `tram_vehicle_msgs`, оставьте **один** из
  двух (colcon не соберёт два пакета с одним именем). Поля сообщений и
  `CMakeLists.txt` у них одинаковые (сверено `diff` с пакетом из датасета), наш
  манифест отличается только строкой `<maintainer>`. Без неё сборка падает —
  берите наш.

## 3. Запуск

1. **Сначала нода, потом bag.** Нода подписывается на входы при старте; то, что
   bag опубликует до подписки, до неё не дойдёт.

   ```bash
   source ~/vectra_ws/install/setup.bash
   ros2 launch tram_state_estimator tram.launch.py
   ```

   Признак готовности — строка в логе:
   `оценщик запущен: шаг 50 мс, карта есть`.

   **Рекомендуем `ros2 launch`**: он подставляет лист `config/tram.yaml` и
   перезапускает ноду при падении (`respawn`). `ros2 run tram_state_estimator
   tram_estimator` без `--params-file` тоже работает правильно: нода сама
   подкладывает лист пакета под параметры запуска (в логе:
   «лист: …/config/tram.yaml … (без --params-file: лист пакета)»), а любой
   `-p имя:=значение` меняет только этот параметр. Параметр `sheet: none`
   возвращает внутренние умолчания (только для имитатора).

2. **Bag — в любом режиме.** Организаторы подтвердили, что режим проигрывания не
   важен. Нода работает по `header.stamp` входов, поэтому `--clock` и
   `use_sim_time` не нужны, но и не мешают (проверено: выход тот же). Скорость
   `-r` до 5 проверена: нода успевает.

   ```bash
   source ~/vectra_ws/install/setup.bash
   ros2 bag play <путь к прогону> -d 3
   ```

   `-d 3` даёт DDS 3 с на обнаружение подписчиков до первого сообщения. Под
   нагрузкой обнаружение занимало до 3,7–5,8 с после старта плеера, а окно
   выставки по GNSS — первые 3 с bag: ноду запускайте заранее, а bag — с
   задержкой не меньше 3 с. Скорость `-r` не обязательно 1: нода оценивает
   темп проигрывания сама (для прогноза во время пауз входов).

3. **Несколько bag подряд.** Рекомендуем перезапускать ноду между прогонами
   (Ctrl+C в терминале 1 и снова `ros2 launch`): каждый прогон — новая выставка
   по GNSS. Без перезапуска тоже работает: разрыв меток (второй bag раньше или
   позже больше чем на 60 с, `--loop`) нода распознаёт как новый прогон и
   выставляется заново по его GNSS; до новой выставки положение идёт по
   прежней (σ положения увеличена на 10 м).

4. **Останов** — Ctrl+C в терминале ноды.

## 4. Топики

Входы (подписка best-effort, глубина 50):

| Топик | Тип | Используется |
|---|---|---|
| `/vehicle/front_bogie_velocity` | `tram_vehicle_msgs/msg/VelocitySensor` | скорость передней тележки, км/ч (подтверждено организаторами) |
| `/vehicle/rear_bogie_velocity` | `tram_vehicle_msgs/msg/VelocitySensor` | скорость задней тележки, км/ч |
| `/vehicle/driver_position_cmd` | `tram_vehicle_msgs/msg/DriverControllerCommand` | позиция ручки −15…+15 |
| `/sensing/gnss/master/fix`, `/sensing/gnss/rover/fix` | `sensor_msgs/msg/NavSatFix` | **только** окно начальной выставки (`init_window_s`, 3 с от первой точки): начальное положение и курс по двум антеннам. Дальше не влияет ни на что |

Выходы (издатель reliable, глубина 10; подписчик best-effort совместим):

| Топик | Тип | Частота | `frame_id` | Содержимое |
|---|---|---|---|---|
| `/result/velocity` | `tram_vehicle_msgs/msg/VelocitySensor` | 20 Гц | `base_link` | `velocity` — продольная скорость, м/с |
| `/result/position` | `nav_msgs/msg/Odometry` | 20 Гц | `map`, `child_frame_id` = `base_link` | `pose.pose.position` x/y/z (раздел 5); `orientation` — курс; `pose.covariance[0]`, `[7]` — σ² положения, м²; `twist.twist.linear.x` — скорость, м/с; `twist.covariance[0]` — σ² скорости |
| `/result/acceleration` | `geometry_msgs/msg/AccelStamped` | 20 Гц | `base_link` | продольное ускорение модели, м/с² |
| `/tram/estimator_status` | `tram_msgs/msg/EstimatorStatus` | 20 Гц | `base_link` | режим (тяга/выбег/торможение/буксование/стоянка), σ, признаки проскальзывания, здоровье датчиков, `valid` |

Метки времени. `header.stamp` всех выходов — время из bag, не часы ноды. Нода
шагает по равномерной сетке 50 мс по меткам входов и публикует каждый шаг с
меткой его узла. Метки монотонны, без нулей.

**Глубина очереди подписчика — не меньше 50.** На старте bag в записи идёт хвост
буфера: несколько секунд меток за доли секунды. Нода обрабатывает его пачкой, до
49 выходов за один вызов. Подписчик best-effort с глубиной 10 и медленным
колбэком может потерять часть этих выходов. После провала входов внутри
прогона (в штатных bag не бывает) нода догоняет сетку пачками до 200 выходов.

**Паузы входов и конец bag.** Если входы молчат дольше 0,1 с (пауза в записи
bag, пауза плеера), нода публикует прогноз по модели на копии своего
состояния, не дальше 2 с от последней метки входа (`pulse_horizon_s`); метки
выхода не идут назад, а когда входы возвращаются, узлы, уже выданные
прогнозом, повторно не публикуются. Поэтому **после конца bag выходит ещё до
2 с прогноза (до 40 выходов)**. Если итоговый дрейф считается по последнему
выходу, а не по последней метке GNSS, на ходу это добавит путь за эти 2 с;
отключить: `pulse_horizon_s: 0.0`.

## 5. Система координат положения

По ответам организаторов (25.09–26.09): плоские координаты **MGRS**, оси по
REP 103, отсчёт — от угла квадрата **37U CB непрерывно** (так записана их карта
pathgraph: x = UTM E − 300 000, y = UTM N − 6 100 000; на границе квадратов
E = 400 км x переходит 100 000 плавно). Точка — **`base_link`**: ось поворота
передней тележки на уровне рельса.

| Ось | Значение |
|---|---|
| `x` | MGRS easting от угла 37U CB, м (на линии ≈ 98 800…103 700) |
| `y` | MGRS northing от угла 37U CB, м (≈ 84 400…86 100) |
| `z` | высота уровня рельса, м: `altitude` из `NavSatFix` (эллипсоид WGS84) минус 3,0 м (высота антенн над `base_link`) |

`frame_id` = `map` (эта система), `child_frame_id` = `base_link`. Положение
публикуется на каждом шаге выхода после начальной выставки (без пропусков на
границе квадратов).

Антенны в `base_link` (tf организаторов): master (−9,873; 0; 3,0), rover
(2,563; 0; 3,0). При выставке `base_link` = master + 9,873/12,436 · (rover −
master), z − 3,0; дальше точка ведётся по карте путей, построенной по
траектории `base_link`.

Параметры ноды (в `config/tram.yaml`):

| Параметр | Значения | По умолчанию |
|---|---|---|
| `projection` | `mgrs` — плоские MGRS; `utm` — абсолютные UTM E/N (зона 37); `enu` — касательная плоскость в первой точке master; `equirect` — формула прежней версии | `mgrs` |
| `mgrs_grid` | код квадрата — непрерывно от его угла; `""` — квадрат каждой точки (Autoware, на границе скачок на 100 км) | `"37UCB"` |
| `mgrs_guard_m` | только при `mgrs_grid: ""`: ближе этого к краю 100-км квадрата положение не публикуется; `0` — выключено | `0.0` |
| `output_point` | `base_link` — ось передней тележки, уровень рельса; `master` — антенна master (на 9,87 м позади вдоль пути и на 3 м выше) | `base_link` |
| `antenna_master_x`, `antenna_rover_x`, `antenna_z` | положение антенн в `base_link`, м | `-9.873`, `2.563`, `3.0` |
| `utm_zone` | зона UTM; `0` — по точке выставки (здесь 37) | `0` |
| `nomap_mode` | без карты (`map_file: ""`): `hold` — положение стоит в точке выставки, `line` — по прямой вдоль начального курса | `hold` |

Внутри нода считает в непрерывной метрической системе (UTM со сдвигом в точку
выставки); в MGRS переводит только при публикации. Подробно —
[POSITION_FRAME.md](POSITION_FRAME.md).

Как поменять параметр: в
`install/tram_state_estimator/share/tram_state_estimator/config/tram.yaml` (или
в `src/.../config/tram.yaml` с пересборкой) под `ros__parameters` исправить
строку, например `mgrs_grid: ""`, и перезапустить launch. Или без правки
файлов: `ros2 run tram_state_estimator tram_estimator --ros-args -p
output_point:=master` — остальные параметры нода возьмёт из листа пакета. Все
параметры ноды есть в листе с комментариями (лист генерируется
`tools/gen_params.py`, тест `test_sheets.py` сверяет его с объявлениями ноды).

## 6. Как смотреть: логи, частота, задержка, ресурсы

**Логи.** Нода пишет в терминал launch (`output=screen`). Копия —
`~/.ros/log/<дата-время>/launch.log`.

```bash
ros2 node list                               # /tram_state_estimator
ros2 topic hz /result/velocity               # ≈ 20 Гц во время проигрывания
ros2 topic echo /result/position --once
ros2 topic echo /tram/estimator_status --field valid
```

`ros2 topic hz` показывает частоту по стенным часам. Сразу после старта bag она
выше 20 Гц: это хвост буфера записи (см. выше).

**Задержка — `tools/ros_probe.py`.** Это отдельная нода-проба, подписка
best-effort, как у судьи. Запуск в третьем терминале **до** bag:

```bash
source ~/vectra_ws/install/setup.bash
python3 <репозиторий>/tools/ros_probe.py --out /tmp/probe.json --idle 10
# после bag и 10 с тишины печатает сводку: частота, задержка, CPU, RSS ноды
```

Проба нужна `python3-psutil` для CPU и RSS: `apt install python3-psutil`. Без
него остальные метрики считаются.

**Наше определение задержки (in2out).** Время по стенным часам пробы:

- от приёма входа `/vehicle/*`
- до приёма первого выхода со `stamp ≥ stamp` этого входа.

В этом выходе показание входа уже учтено. Задержка около 50 мс заложена в схему:
показание попадает в следующий узел сетки 50 мс. Этот узел считается, когда
приходит следующее сообщение с меткой не меньше узла.

**Оговорка про старт bag.** Первые 2–3 с каждой записи — хвост буфера регистратора:
метки сообщений на 2–6 с старше момента записи, и они приходят пачкой. Поэтому:

- сводка пробы даёт in2out и по всему прогону, и «установившийся» — без первых 2 с
  после первого выхода;
- если считать задержку как `now() − header.stamp` по `/clock`
  (`use_sim_time`), первые 2,45 с bag дают до 2,5 с «задержки». Это свойство
  записи, а не ноды. Дальше по этой формуле p99 6,7 мс.

**CPU и ОЗУ.**

```bash
pidstat -u -r -p $(pgrep -f lib/tram_state_estimator/tram_estimator) 1   # sysstat
top -p $(pgrep -f lib/tram_state_estimator/tram_estimator)
```

То же пишет проба: CPU (% одного ядра) и RSS раз в 1 с, наклон RSS для проверки
утечки. Ещё проба сверяет положение с GNSS master из того же bag (санити) в той
системе, в которой публикует нода. Ошибка считается как у судьи: без вычета
скачка на границе 100-км квадратов (`mean_m`). С вычетом — справочно
(`mean_m_unwrapped`), `square_mismatch` — сколько пар по разные стороны границы. Полный замер с лимитами ТЗ (2 ядра, 512 МБ) — `tools/measure_realtime.sh`
(раздел 7).

## 7. Docker (по желанию)

Всё то же в контейнере одной командой. Нужен Docker с Compose v2.

```bash
cp .env.example .env         # DATA_DIR — папка с прогонами, BAG — какой проигрывать
docker compose up --build    # сборка образа и живой прогон: нода + bag + проба + мост + страница
docker compose run --rm test # colcon build + тесты без сети (~5–9 мин); timing-тест: test -m timing
docker compose run --rm eval # офлайн-оценка tools/eval.py (нужны данные)
```

Сервисы `docker compose up`:

| Сервис | Что делает |
|---|---|
| `estimator` | `ros2 launch tram_state_estimator tram.launch.py` |
| `player` | ждёт подписчиков и выполняет `ros2 bag play /data/$BAG -d 2`; `PLAY_LOOP=1` — по кругу |
| `probe` | `tools/ros_probe.py`: промежуточная сводка раз в 30 с и итог. Файлы — `out/probe/summary.json` |
| `bridge` | rosbridge websocket, `ws://localhost:9090`; только для чтения (`docker/bridge.sh`; `ROSBRIDGE_OPEN=1` — открытый) |
| `web` | страница симулятора, `http://localhost:8080` |

`--build` нужен после каждого обновления исходников: нода запускается из `/ws`
образа, а без `--build` compose возьмёт старый образ.

Базовый образ закреплён по digest (`docker/Dockerfile`). Интернет нужен только
при сборке образа: apt, pip `rosbags`. Сама сборка пакетов внутри сети не требует.

У `estimator` нет `restart`: `player` и `probe` работают в его сетевом, IPC и
PID пространствах, а перезапущенный контейнер получил бы новые. Если контейнер
`estimator` упал целиком: `docker compose up -d --force-recreate`.

Скрипты проверки (Git Bash или Linux, из корня репозитория):

```bash
tools/ros_smoke.sh                       # ROS-смоук на фикстуре: данные не нужны
tools/ros_smoke.sh --bag 30618_98161270  # 30 с настоящего прогона
tools/ros_smoke.sh --gnss-window 3 --repeat 10   # GNSS только первые 3 с по меткам, 10 раз
tools/measure_realtime.sh --bag 30618_e9a34502   # x1, нода с --cpus 2 --memory 512m
```

`ros_smoke.sh` проверяет в одном контейнере:
- ≥ 19 Гц;
- in2out p99 < 100 мс в установившемся режиме;
- ≥ 95 % узлов сетки;
- 0 NaN;
- `frame_id`;
- нода жива до конца;
- останов по SIGINT.

С `--gnss-window 3` в bag остаются только первые 3 с GNSS по меткам. Тогда
обязательна ещё одна проверка: выставка прошла, средняя 3D против GNSS
фикстуры < 10 м.

Ещё проверки `ros_smoke.sh`: `/result/position` — не меньше 95 % узлов сетки и
не больше, чем `/result/velocity` (до выставки положение не публикуется). Если
нода публикует MGRS, а кусок bag лежит в одном квадрате, выход и эталон должны
быть в одном 100-км квадрате.

Скрипт сверяет и обвязку: получила ли проба все входы bag. Если проба потеряла
начало bag (гонка обнаружения DDS на старте проигрывания) и какая-то проверка
не прошла, прогон помечается «НЕ ЗАСЧИТАН» — как прогон скрипта. Для жюри это
не оправдание: если нода не получила окно GNSS, положения в этом прогоне нет
(риск 16). В статистике ноды такой прогон — срыв выставки: 1 из 25 прогонов
сценария «GNSS 3 с» (20 — 25.09 до правок, 5 — на пробном слиянии с потоком
position).

`measure_realtime.sh` без `--build` проверяет, что `/ws/src` образа совпадает с
`ros2_ws/src` (кроме `test/`), иначе не запускается: мерился бы старый код.

`measure_realtime.sh` пишет:
- частоту;
- задержку p50/p95/p99/max;
- CPU;
- RSS по минутам;
- проверку утечки (на bag короче ~90 с — «н/д»);
- разрывы выхода > 0,3 с: с разрывом входов (пауза в записи bag) или без него.

Результаты — в `out/realtime/<tag>/summary.{json,md}`.

## 10. Если что-то не так

| Симптом | Причина и что делать |
|---|---|
| `colcon build`: `Duplicate package names` | два `tram_vehicle_msgs` в workspace — оставить один (раздел 2) |
| `colcon build`: ошибка catkin_pkg про maintainer | собирается оригинальный `tram_vehicle_msgs` без `<maintainer>` — взять наш |
| `ros2 bag play`: не найден тип `tram_vehicle_msgs/...` | в терминале плеера не выполнен `source install/setup.bash` |
| выходов нет | нода запущена после bag или в другом `ROS_DOMAIN_ID` / `ROS_LOCALHOST_ONLY`; проверить `ros2 node list`, запустить ноду раньше bag |
| выход 100 Гц, скорость неверная | нода запущена с `sheet: none` (внутренние умолчания имитатора) — убрать этот параметр; `ros2 run` без параметров сам берёт лист пакета |
| нет строки «карта есть» | не найден `config/track_map.npz` в `share/tram_state_estimator` — пересобрать пакет; без карты положение стоит в точке выставки (`nomap_mode: hold`; `line` — по прямой вдоль начального курса) |
| первые секунды частота > 20 Гц, задержка по `/clock` до 2,5 с | хвост буфера записи в начале bag (раздел 6) |
| подписчик теряет выходы на старте | глубина очереди < 50 (раздел 4) |
| `/result/position` не публикуется | в начале bag нет GNSS master — якоря нет; до первой годной точки master положение не публикуется, скорость при этом верна |
| Docker: порт 9090 или 8080 занят | `BRIDGE_PORT` / `WEB_PORT` в `.env` |
| Docker: `player` пишет «bag не найден» | `DATA_DIR` в `.env` — папка, где лежат каталоги прогонов; `BAG` — имя каталога |
