### Как запускать проверки

Все команды выполняются из корня репозитория. `docker compose` и `tools/*.sh` - с хоста (Linux
или Git Bash; `docker compose` в PowerShell пишется так же). `ros2` и
`python3 tools/ros_probe.py` - в окружении ROS 2 с собранным пакетом
([JURY.md §2-3](JURY.md#3-запуск)); `ros2 topic`, `ros2 node` и `ros2 param` - во время
проигрывания записи. Пути к коду даны от `pkg/` = `ros2_ws/src/tram_state_estimator/`: модули
`*.py` лежат в `pkg/tram_state_estimator/`, тесты - в `pkg/test/`.

Собрать пакеты и прогнать все тесты без сети.

```bash
docker compose run --rm test
```

Прогнать отдельные тесты по имени: аргументы после `test` уходят в pytest.

```bash
docker compose run --rm test -k <имя_теста>
```

Запустить ноду.

```bash
ros2 launch tram_state_estimator tram.launch.py
```

Проиграть запись во втором терминале.

```bash
ros2 bag play <папка_записи> -d 3
```

Посчитать точность и инъекции аномалий (нужны данные в `DATA_DIR`).

```bash
docker compose run --rm eval
```

Поднять демо: нода, запись, проба, мост и страница http://localhost:8080.

```bash
docker compose up --build
```

## 1. Входы, выходы, время, система координат

### 1.1. Входы

- **Как выполнено.** Подписка best-effort, глубина 50, на `/vehicle/front_bogie_velocity`,
  `/vehicle/rear_bogie_velocity` и `/vehicle/driver_position_cmd`. Скорость тележек переводится
  из км/ч в м/с по листу (`meas_units: km_h`), ручка вне ±15 ограничивается.
- **Где в коде.** `tram_node.py` (подписки в `TramEstimatorNode.__init__`), `runner.py`
  (`Runner.on_wheel`, `Runner.on_handle`, `HANDLE_LIMIT`), `pkg/config/tram.yaml`.
- **Результат.** Подписки на 3 входа и 2 топика GNSS fix; топики `/sensing/gnss/*/vel` не
  используются.

Показать подписки ноды.

```bash
ros2 node info /tram_state_estimator
```

### 1.2. Выход скорости

- **Как выполнено.** Сообщение `tram_vehicle_msgs/VelocitySensor`, поле `velocity` в м/с,
  публикуется на каждом шаге сетки 50 мс.
- **Где в коде.** `tram_node.py` (`_publish`).
- **Результат.** Пар скорости 99,99 % меток GNSS, NaN 0 ([EVAL §3.1](EVAL.md#31-скорость)).

Показать сообщения скорости.

```bash
ros2 topic echo /result/velocity
```

### 1.3. Выход положения

- **Как выполнено.** Сообщение `nav_msgs/Odometry`, `pose.pose.position` x/y/z в метрах системы
  судьи (подраздел 1.4), публикуется после выставки по GNSS.
- **Где в коде.** `tram_node.py` (`_publish`), `runner.py` (`Position`), `geodesy.py`, `body.py`.
- **Результат.** Сырые x, y, z против эталона судьи: средняя 3D 3,81 м, пар с ошибкой > 1 км: 0.
  Шагов без положения после первого опубликованного: 0 ([EVAL «Главное»](EVAL.md#главное)).

Показать одно сообщение положения с QoS судьи.

```bash
ros2 topic echo --once --qos-reliability best_effort /result/position
```

Проверить систему координат и точку выхода.

```bash
docker compose run --rm test -k "test_output_frame_is_mgrs_by_default or test_output_point_is_base_link"
```

### 1.4. Система координат и начальная позиция

- **Как выполнено.** Система судьи по ответу организаторов: плоские MGRS от угла квадрата 37UCB
  непрерывно, точка `base_link`, z - уровень рельса
  ([JURY.md §4](JURY.md#4-система-координат-положения)). Начальная позиция - выставка по GNSS
  в первые 3 с bag: якорь, высота, курс по паре антенн. Другие системы задаются параметром
  `projection`: `utm`, `enu` от первой точки master, `equirect`.
- **Где в коде.** `geodesy.py` (`Frame`), `runner.py` (`Position`); параметры `projection`,
  `mgrs_grid`, `output_point` в `pkg/config/tram.yaml`.
- **Результат.** С чистого клона положение идёт с метки +1,0 с от первого выхода (выставка по
  5 точкам GNSS): x 99 052,3, y 84 985,5, z 171,6.

Показать систему координат выхода.

```bash
ros2 param get /tram_state_estimator projection
```

### 1.5. Карта pathgraph и режим без карты

- **Как выполнено.** Карта пакета `pkg/config/track_map.npz` - pathgraph организаторов плюс карта
  из GNSS обучающих записей за его концами (конечные, ветки). Курсор идёт по оси пути с привязкой к
  остановкам. Без карты (`map_file: ""`) положение идёт по пути колёс от выставки
  (`nomap_mode`: `hold` или `line`).
- **Где в коде.** `track_map.py` (`TrackMap.load`, `TrackMap.from_pathgraph`),
  `analysis/build_map.py`.
- **Результат.** Поперёк pathgraph организаторов ср. 0,011 м ([EVAL §3.2](EVAL.md#32-положение-mgrs-от-37ucb-точка-base_link-ошибки-в-непрерывных-координатах)).
  В логе запуска строка «карта есть»: точек осей 17554, остановок 51, конечных 4, веток у
  конечных 3.

Проверить режимы без карты.

```bash
docker compose run --rm test -k test_no_map_fallback_modes
```

### 1.6. Метки времени

- **Как выполнено.** Ядро шагает по сетке, построенной по меткам входов. Узлы кратны 50 мс и
  совпадают с метками GNSS (кратны 0,1 с), выход получает метку своего узла.
- **Где в коде.** `runner.py` (`Runner`, `_start`, `tick`), `tram_node.py` (`to_msg`).
- **Результат.** Пар положения 100,00 % меток GNSS fix
  ([EVAL §3.2](EVAL.md#32-положение-mgrs-от-37ucb-точка-base_link-ошибки-в-непрерывных-координатах)).

Показать метки времени выхода.

```bash
ros2 topic echo /result/velocity --field header.stamp
```

Проверить, что узлы сетки кратны шагу и совпадают с метками GNSS.

```bash
docker compose run --rm test -k "test_grid_nodes_are_multiples_of_dt_without_drift or test_gnss_stamps_fall_on_grid_nodes"
```

### 1.7. `frame_id` и корректность Odometry

- **Как выполнено.** У `/result/position` `frame_id` `map` (MGRS 37UCB), `child_frame_id`
  `base_link`; у `/result/velocity` - `base_link`. В ковариациях нет нулевой диагонали: x, y -
  σ пути, z - высота карты, крен, тангаж, курс. `twist.linear.x` - скорость.
- **Где в коде.** `tram_node.py`: параметры `frame_id`, `child_frame_id`, `_publish`, константы
  `ROLL_SD`…`R_CURVE_MIN`.
- **Результат.** Смоук: `frame_id: map / base_link` - PASS. |вдоль| ≤ 2σ_s в 92,8 % времени
  (EVAL §3.2), скорость внутри ±2σ в 96,0 % (EVAL §3.1).

Проверить, что в ковариациях нет нулевой диагонали.

```bash
docker compose run --rm test -k test_odometry_covariances_have_no_zero_diagonal
```

Прогнать ROS-смоук: нода, 30 с записи и проба в одном контейнере.

```bash
tools/ros_smoke.sh
```

### 1.8. QoS

- **Как выполнено.** Издатели с QoS по умолчанию (reliable), они совместимы с подписчиком
  best-effort, как у судьи.
- **Где в коде.** `tram_node.py` (`create_publisher`).
- **Результат.** Проба с подпиской best-effort получает все выходы: 24 081 из 24 081 узла сетки
  ([EVAL §7](EVAL.md#7-реальное-время)).

Показать QoS издателя и подписчиков.

```bash
ros2 topic info -v /result/velocity
```

### 1.9. Онлайн-публикация без данных «из будущего»

- **Как выполнено.** Шаг публикуется сразу при приходе входа. Если входы молчат, пульс публикует
  прогноз не дальше 0,2 с. Сетка шагает только до метки пришедшего сообщения. Точка GNSS ждёт,
  пока сетка пройдёт её метку, и сравнивается с положением на свою метку. Стартовый всплеск
  сортируется только среди уже пришедших сообщений (0,1 с).
- **Где в коде.** `tram_node.py` (`_dispatch`, `_extrapolate`), `runner.py` (`Runner.tick`,
  `Position`: `CORR_DELAY`, `CORR_HIST_S`; `StartSorter`).
- **Результат.** 20,0 Гц по меткам (EVAL §7). Оценка идёт той же связкой в порядке записи bag
  ([EVAL §2](EVAL.md#2-методика)).

Проверить, что GNSS не двигает сетку, а стартовый всплеск сортируется по меткам.

```bash
docker compose run --rm test -k "test_gnss_never_moves_the_grid or test_start_sorter_orders_by_stamp_then_passes_through"
```

## 2. GNSS

### 2.1. Выставка и коррекция

- **Как выполнено.** Коррекцию разрешают PDF и ответ организаторов, README датасета - только
  выставку ([TZ_REQUIREMENTS.md](TZ_REQUIREMENTS.md#gnss-расхождение-источников)). Первые 3 с
  от первой годной точки - выставка: якорь, высота, курс по паре антенн. После окна точки GNSS
  поправляют только положение вдоль пути, выбросы отбраковываются (`gnss_correction: true`).
  С `false` GNSS нужен только для выставки.
- **Где в коде.** `runner.py` (`Position`: окно выставки, раздел «коррекция по GNSS»), параметры
  `init_window_s`, `gnss_*`.
- **Результат.** Вагон 30618, 3D ср.: 1,91 м при GNSS 3 с, 1,76 м при редких пачках, 1,48 м при
  GNSS весь прогон ([EVAL §5.1](EVAL.md#51-сценарии-доступности-gnss-toolseval_gnsspy)).

Прогнать тесты коррекции по GNSS.

```bash
docker compose run --rm test -k gnss_correction
```

### 2.2. GNSS вне контура скорости

- **Как выполнено.** Скорость считает ядро только по тележкам и ручке, сетку двигают тоже только
  они. Точка GNSS встаёт в очередь положения, ядро её не получает.
- **Где в коде.** `runner.py` (`Runner.on_fix`), `estimator_core.py` (GNSS не принимает).
- **Тесты.** `test_flag_off_is_bit_identical_to_main`, `test_first3_with_correction_is_identical`,
  `test_whole_slice_gnss_real_fixture_speed_same_position_closer` (входят в команду из 2.1).
- **Результат.** При GNSS весь прогон сетка и скорость совпали с режимом «GNSS 3 с» в 5 из 5
  прогонов ([EVAL §5](EVAL.md#5-gnss-весь-прогон-bag-жюри-с-полным-gnss)).

Сравнить сценарии доступности GNSS на отложенных записях (нужны данные и образ с numpy).

```bash
python3 tools/eval_gnss.py
```

### 2.3. GNSS только в первые секунды

- **Как выполнено.** После первых секунд положение идёт по пути колёс, карте путей и привязкам
  к остановкам. Без выставки `/result/position` не публикуется, скорость публикуется.
- **Где в коде.** `runner.py` (`Position`), `track_map.py`.
- **Результат.** При GNSS только в первые 3 с: 3D ср. 3,81 м на всех 15 записях, 1,91 м на
  вагоне 30618 ([EVAL «Главное»](EVAL.md#главное)).

Прогнать ROS-смоук с GNSS только в первые 3 с.

```bash
tools/ros_smoke.sh --gnss-window 3
```

## 3. Реальное время (критерий 4)

Два замера ([EVAL §7](EVAL.md#7-реальное-время), сводки в `docs/data/realtime/`):

- **Отчётный.** Полная запись `30618_e9a34502` (20 мин), скорость 1x, нода в своём контейнере
  `--cpus 2 --memory 512m`, рядом проба `tools/ros_probe.py` с подпиской best-effort, как у
  судьи.
- **Пауза входов.** Запись `30618_af7496f0` (4,5 мин): на t+142 с поток `/vehicle/*`
  прерывается на 0,95 с, GNSS идёт. Метки входов без разрыва, после паузы сообщения приходят с
  опозданием. Прогноз пульса идёт не дальше 0,2 с от последней метки (4 узла сетки), поэтому
  вернувшиеся входы ждут выхода не дольше этого горизонта. Замер тем же скриптом с лимитами ТЗ.

Замерить реальное время ноды с лимитами ТЗ.

```bash
tools/measure_realtime.sh --bag 30618_e9a34502 --cpus 2 --memory 512m --build
```

| Опция | Что делает |
|:---|:---|
| `--bag 30618_e9a34502` | запись из `DATA_DIR` |
| `--cpus 2 --memory 512m` | лимиты ТЗ на контейнер ноды |
| `--build` | пересобрать образ из рабочего дерева перед замером |

Запустить пробу, как у судьи, до проигрывания записи.

```bash
python3 tools/ros_probe.py --out /tmp/probe.json --idle 10
```

| Опция | Что делает |
|:---|:---|
| `--out /tmp/probe.json` | куда записать JSON-сводку |
| `--idle 10` | выйти после 10 с тишины после первого сообщения |

### 3.1. Задержка

- **Как выполнено.** Шаг сетки 50 мс, показание попадает в ближайший следующий узел, шаг связки
  занимает единицы мс.
- **Где в коде.** `runner.py`, `tram_node.py` (`_dispatch`).
- **Результат, отчётный замер.** p50 51,2 мс, p99 54,2 мс, максимум 169,4 мс; больше 250 мс -
  0 из 46 186 пар.
- **Результат, пауза входов.** p50 50,9 мс, p99 97,7 мс по всем парам (его даёт стартовый
  всплеск bag; без первых 2 с bag - 53,3 мс). Максимум 181,5 мс, больше 250 мс - 0 из 10 456 пар.
  С GNSS только в первые 3 с - максимум 181,4 мс, 0 пар.
- **Точки GNSS в паузе входов.** Они ждут возвращения `/vehicle/*`: если считать задержку и от
  GNSS, максимум 805,5 мс.

### 3.2. Частота

- **Как выполнено.** Сетка 50 мс, то есть 20 Гц (ТЗ рекомендует 20-50). Пульс закрывает паузы
  входов до 0,3 с прогнозом не дальше 0,2 с; при более долгой паузе записи выход ждёт входов.
- **Где в коде.** `pkg/config/tram.yaml` (`dt: 0.05`), `tram_node.py` (`_extrapolate`).
- **Результат.** 20,0 Гц, 24 081 выход из 24 081 узла сетки.

Измерить частоту во время проигрывания записи.

```bash
ros2 topic hz /result/velocity
```

### 3.3. CPU и ОЗУ

- **Как выполнено.** Один поток (`rclpy.spin`, однопоточный исполнитель), numpy без параллельных
  вычислений. Очереди ограничены: шагов за вызов `MAX_STEPS`, точек коррекции `CORR_MAX_Q`,
  подтверждений `CORR_PEND_MAX`, история пути `CORR_HIST_S`.
- **Где в коде.** `tram_node.py` (`main`), `runner.py`.
- **Результат.** В среднем 10,3 % одного ядра, максимум 16,0 %; RSS 70 МБ при лимите контейнера
  512 МБ.

Показать загрузку процесса ноды.

```bash
top -p $(pgrep -f tram_estimator)
```

### 3.4. Без утечек

- **Как выполнено.** Очереди ограничены, буферы кольцевые: память не растёт с длиной прогона.
- **Где в коде.** `runner.py`, `plant.py`.
- **Результат.** Рост RSS 0,00 МБ/мин за 20 мин (наклон RSS в `tools/measure_realtime.sh`).

Проверить, что память связки ограничена на долгом прогоне.

```bash
docker compose run --rm test -k test_long_run_memory_is_bounded
```

### 3.5. Без гонок

- **Как выполнено.** Подписки и таймер пульса выполняются в одном потоке исполнителя, прогноз
  пульса считается на копии связки.
- **Где в коде.** `tram_node.py` (`_extrapolate`), `runner.py` (`Runner.fork`).
- **Результат.** Офлайн-оценка детерминирована: два прогона дают побайтно одинаковые JSON
  ([EVAL §1](EVAL.md#1-как-запустить)).

Прогнать тесты пульса, повторов, темпа проигрывания и детерминизма.

```bash
docker compose run --rm test -k "node_robust or determinism"
```

### 3.6. Работа без вмешательства

- **Как выполнено.** Нода сама переживает паузы, второй bag, `--loop` и скачки меток. Launch
  перезапускает её при падении (`respawn`).
- **Где в коде.** `runner.py` (`Runner.reset`, запасная выставка), `pkg/launch/tram.launch.py`.
- **Результат.** 20-минутный прогон: нода жива до конца, останов по SIGINT с кодом 0
  ([JURY.md §6](JURY.md#6-логи-частота-задержка-cpu-и-ram)).

Проиграть две записи подряд в одну ноду.

```bash
tools/ros_e2e.sh --bag 30618_bab2fe58 --bag 30618_98161270 --build
```

### 3.7. Сборка без интернета

- **Как выполнено.** Зависимости - только пакеты базового образа ROS 2 Humble: `rclpy`,
  стандартные сообщения, numpy, yaml.
- **Где в коде.** `ros2_ws/src/*/package.xml`.
- **Результат.** Чистый `ros:humble-ros-base` с `--network none`: 3 пакета за 4,9 с, строк warning
  и error 0. Сервис `test` тоже собирает без сети (`network_mode: none`), команда - в
  [разделе 0](#как-запускать-проверки).

## 4. Устойчивость (критерий 3)

Числа - из инъекций аномалий в отложенные записи ([EVAL §6](EVAL.md#6-инъекции-аномалий)): MAE
скорости модели и в скобках база «только колеса» на тех же данных. Всего 12 видов аномалий на 3
записях, 36 прогонов, падений связки 0. Команда расчёта - `docker compose run --rm eval`
([раздел 0](#как-запускать-проверки)).

### 4.1. Снижение доверия при проскальзывании

- **Как выполнено.** Показания в сторону срыва не принимаются, скорость ведёт модель, σ скорости
  расширяется. Флаги `slip`, `slip_all`, `ambiguous`, `valid`.
- **Где в коде.** `estimator_core.py` (`Estimator._correct`, `_slip_all_update`,
  `_slip_all_return`), `tram_msgs/EstimatorStatus`.
- **Результат.** Юз −30 % обеих тележек: MAE 0,183 м/с (база 1,772), флаг срыва в 99 % окна.
  Буксование +30 %: 0,211 (база 0,862).

Следить за флагами проскальзывания и сцепления.

```bash

```

### 4.2. Статус проскальзывания и адаптация

- **Как выполнено.** Плюс к критерию 3: `slip`, `slip_all` (+1 буксование, −1 юз), оценка
  сцепления `mu`, шум показаний `meas_noise`, масштабы привода `k_traction`, `k_brake`.
- **Где в коде.** `estimator_core.py`, `tram_node.py` (`_publish`: поля `EstimatorStatus`).
- **Результат.** Поля публикуются на каждом шаге (20 Гц); команда та же, что в 4.1.

### 4.3. Кратковременные пропуски

- **Как выполнено.** Шаг без новых показаний - только прогноз. Долгий разрыв - разомкнутый режим
  по ручке.
- **Где в коде.** `runner.py` (`wheel_timeout_s`, `handle_timeout_s`), `estimator_core.py`
  (`step_open_loop`).
- **Результат.** Пропуск 2 с: MAE 0,069 м/с (база 0,361); инъекции `dropout`, `gap_all`.

### 4.4. Выбросы

- **Как выполнено.** Проверка правдоподобия по невязке и пределу ускорения колеса, скачок против
  тренда.
- **Где в коде.** `estimator_core.py` (`_correct`, `step`).
- **Результат.** Выбросы ×3: MAE 0,035 м/с (база 0,213); инъекция `outliers`.

### 4.5. Отказ датчика

- **Как выполнено.** Диагностика залипания и обрыва; после восстановления датчик снова
  принимается.
- **Где в коде.** `estimator_core.py` (`_diagnose`).
- **Результат.** Отказ передней тележки на 60 с: MAE 0,028 м/с (база 2,378), остаток пути 0,1 м
  (база 186,2 м); инъекции `front_zero`, `rear_drop`, `both_stuck`.

### 4.6. Нет расходимости

- **Как выполнено.** При неконечном состоянии ядро сбрасывается с сохранением пути. NaN в выход
  не уходит.
- **Где в коде.** `runner.py` (`reset_core`), `tram_node.py` (`_publish`: последний рубеж).
- **Результат.** NaN в выходе 0, падений связки 0 ([EVAL §3](EVAL.md#3-итог-на-отложенных)).

Проверить сброс ядра при неконечном состоянии.

```bash

```

### 4.7. Нода не падает и восстанавливается

- **Как выполнено.** Сообщение с меткой не числом или ≤ 0 отбрасывается, значение не число или
  невозможное - тоже. Скачки меток подтверждаются. Исключение в колбэке не роняет ноду, launch
  перезапускает её (`respawn`).
- **Где в коде.** `runner.py` (`Runner`), `tram_node.py` (`_input`, `_fail`),
  `pkg/launch/tram.launch.py`.
- **Результат.** NaN во входе и скачок метки +30 с - «в пределах нормы» (EVAL §6).

## 9. Консоль ноды

Нода пишет в терминал `ros2 launch`, копия - в `~/.ros/log/`.

- **При запуске.** Блок настроек с первой строкой `оценщик запущен`: версия пакета и отпечаток
  кода (`код sha`, считается так же, как «Код пакета: sha» в шапке EVAL.md), лист параметров,
  вагон и масштаб колёс, карта путей (точки, остановки, конечные, ветки), система выхода (MGRS
  37UCB, точка `base_link`, `frame_id`), правило GNSS, шаг сетки и частота, входные топики.
- **Во время работы.** «входы пошли», «положение есть» после выставки по GNSS и строка состояния
  раз в 10 с времени bag: частота, ручка и режим ядра, скорость, x/y/z и σ, число принятых
  тележек, флаги (срыв, «стоим или скользим», недостоверно, прогноз пульса).
- **Предупреждения.** Только об отклонениях (сброс связки, разрыв меток, нет выставки по GNSS), с
  ограничением частоты.
- **При останове (Ctrl+C).** Итог: выходы, входы по видам, отброшенные метки и значения, сбросы,
  ошибки в колбэках, время шага связки. Выход без трассировки.

Пример строки состояния:

```text
t+20 с | 20.0 Гц | ручка -8, режим ядра: торможение | v 1.99 м/с (7.2 км/ч) ±0.05 | x 99064.2 y 84996.9 z 171.5 ±0.3 м | тележки 2/2 | норма
```
